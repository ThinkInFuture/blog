1. 出发点：注意力每步要什么

从已经认识的标准多头注意力（MHA）看起。生成第 N 个 token 时，输入只有 1 个新 token，但注意力公式要求这个新 token 的 Q 与前面全部 N 个 token 的 K/V 做点积——新的是 Q，要用的却是历史。历史的 K/V 从哪来？要么每步重算，要么存下来。存下来的那两个张量，就是 KV Cache：

d_model = 4096"] --> Proj["Q/K/V 三个投影
每个都输出 32 个头（4096 维）"] Proj --> Cache["KV 缓存
每 token 追加 2·H·d = 8192 元素 = 16KB"] Proj --> Q["Q（新 token 的 32 个头）"] Cache --> Attn["注意力计算
Q 与缓存里全部 L 个 K 点积 → softmax → ×V"] Q --> Attn Attn --> Out["输出（加权和）"] Note["每个 Q 头都要扫过全部历史
→ 算力 O(L)、缓存 O(L)"] -.-> Attn
图 1 · 标准多头注意力的宏观流程（复用自《多头注意力机制精读》图 MHA-1）：Q/K/V 三个投影各自独立，K/V 追加进缓存，注意力用新 Q 扫缓存里全部 L 个 K

读图 1 的三个要点：一，Q/K/V 投影每个 token 都要做，但只有 Q 是一次性的——用完就扔；二，K/V 是历史的公共财产，后面的每个 token 都要来读，所以值得存；三，缓存每 token 每层追加 2·H·d = 2×32×128 = 8192 个 fp16 元素，正好 16KB——这个数字后面全程要用。

2. 没有缓存会怎样：839 万行重算账

如果坚持不存，代价是每一步都把整个前缀重新过一遍投影。生成第 1 个 token 投影 1 行，第 2 个 token 重算 2 行（第 1、第 2 个），第 4096 个 token 要重算 4096 行。把生成 4096 个 token 的投影行数加起来：

图 2 · 无缓存的投影量是 O(L²)：生成 4096 个 token 需要 839 万行投影；有缓存后每行历史只投影一次

3. 缓存里存的是什么：64 层 × K/V 两个抽屉

KV Cache 不是一个大数组，而是每一层各存各的：输入每穿过一个 Block，就把该 token 在这一层的 K 和 V 追加进这一层自己的缓存。以 64 层模型为例，全模型共有 64 对「K 抽屉 + V 抽屉」：

图 3 · 缓存的组织：64 层 ×（K + V）两个张量；Q 用完即弃不存，K/V 逐层逐行追加

注意这份账只算了一条请求。并发 8 条 32k 请求，缓存就要 256GB——比模型权重本身大得多。所以工程上的两个问题自然浮出来：怎么把零散的缓存管起来不浪费（第 6 章），怎么把每 token 的 16KB压下去（第 7 章）。

5. prefill 与 decode：两种写法

生成过程分两段，缓存的写入方式完全不同——prefill 一次写满，decode 每步追加一行：

图 5 · prefill 一次并行写满 512 行，decode 每步串行追加 1 行（全模型 1MB）——TTFT 与吞吐分别卡在两段上

为什么两段要分开对待：prefill 是计算密集的大矩阵（512 行一起算，算力打满），decode 是访存密集的小向量（每步 1 行，显存带宽决定速度）——推理引擎的调度、 batching、块预分配全部围绕这个差异设计。

6. 块池管理：逻辑连续、物理散放

缓存按需长高，那显存怎么分配？最朴素的办法是按最大长度整段预留——序列最长可能 4096 行，就先留 4GB。问题是绝大多数序列用不满：预留的显存大量闲置，还无法给别的请求复用。块池（PagedAttention 的思路）把缓存切成固定小块，按需领取、用完归还，物理上不必连续，靠一张块表把逻辑序列拼回来：

图 6 · 块池三视图：逻辑连续（上）→ 块表翻译（中）→ 物理散放（下，蓝色为该序列领到的块）；按块分配让闲置显存可共享
块池的三个直接收益
  • 按需领用：写多少行领多少块，不用为「可能的最长」预付整段显存；
  • 碎片可控：外部碎片消失（块随便放），内部碎片封顶每序列最后半个块（本例 16 token / 16MB）；
  • 前缀共享：两条请求的前缀相同，前缀块在块表里指向同一物理块——多轮对话里系统提示词只存一份。

第五条省法：KV 量化（与前四条正交） 存储精度从 fp16 降到 fp8 或 int8，16KB 直接砍半到 8KB，任何架构都能叠加；代价是数值容差——精度敏感的场景要做逐位验证（站内《精度一致性类参数》篇展开的就是这类开关）。
