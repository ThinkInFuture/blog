1. 先给结论：说法成立，但要精确到"哪个开关"

"v2 之后 DSA-CP 日落、换成 PCP"——方向对，细节要校准。源码里的实际情况分三层：

  • 层一 · 文件级标注：dsa_cp.py（2291 行）里，Legacy 实现与 PCP 实现同住一个文件，中间一条分界注释写着 Legacy DSA-CP implementation (TP/SP group)——"Legacy"是源码自己的用词，不是社区传言；
  • 层二 · 开关级互斥：两套实现各有开关（Legacy 靠 additional_config "enable_dsa_cp": true，PCP 靠启动参数 --prefill-context-parallel-size > 1），同时打开直接抛错——互斥说明它们是同一问题的两代答案，不是两个特性；
  • 层三 · 引擎级绑定：PCP 只在 Model Runner V2 上可用（v1 引擎配 PCP 直接启动失败，报错原文就是"PCP is not supported"）——"v2 之后换 PCP"在引擎层面完全成立。
一句话结论DSA-CP 没有被删除（Legacy 路径仍在、开关仍生效），但主线的新增量都在 PCP 上：上游 vLLM 把 prefill 上下文并行做成了通用能力（PCPManager），vllm-ascend 的动作是"写个壳接上去"，而不是继续养自己的私搭通道。DSA-CP 进入维护态，PCP 是它的继任者。

2. Legacy DSA-CP：一条私搭的 prefill 通道

先回忆 DSA-CP 是干什么的（展开版见姊妹篇《SP MoE 与 DSA-CP》）：DSA 的 KV cache 按 sequence 分片存在 TP 组各卡上（省显存），但 prefill 的 query 要看全序列——Legacy DSA-CP 的全部复杂性，都在自己管理这层分片：

  • 自己的 metadata 族（DSACPMetadata / AscendDSAReqMetadata / AscendDSACPLayerMetadata），自己的分片布局与 slot 换算；
  • 自己的通信编排：门口 all-gather 拼全量（或 #18671 后的"SP 分片直通"协商）、o_proj 的 A2A head 互换、部分和归约——全是 DSA-CP 文件内的私有逻辑；
  • 自己的调度耦合：跟 SP MoE 的握手（supports_sequence_parallel_input 那套三方协商）也是它私有的。

私搭通道的代价在《SP MoE 与 DSA-CP》里已经踩过一轮：每加一个邻居（SP、PD 分离、投机解码）都要在通道口协商一次，#18671 修的"每层 AG 拼全量"冗余正是这类协商的学费。vLLM 上游也意识到了这个问题的通用性——prefill 长上下文切分到多卡，是所有长序列模型都要的，不该由 DSA 一家私搭——于是上游 vLLM 自己做了 PCP。

3. PCP：接上上游的"正道"

PCP（Prefill Context Parallelism）的原理一句话：把 prefill 的输入 token 序列切成 N 份分给 N 张卡并行算，算完合并。它与 DSA-CP 解决的是同一件事（单卡 prefill 太长太慢），但位置完全不同：

Legacy DSA-CPPCP
开关additional_config "enable_dsa_cp"（昇腾私有）--prefill-context-parallel-size（上游通用参数）
切分发生地attention 后端内部（metadata 层私搭）Model Runner 的 batch 分区（引擎层统一做）
引擎要求v1/v2 均可仅 v2（v1 直接报错拒绝）
调度器感知无（后端自旋）有（scheduler 知道 batch 被切了）
邻居兼容逐个协商（SP 直通是 #18671 补的）框架位（PP/MM/LoRA/投机 显式边界）
KV cache 形态分片存储、按需聚合各 rank 写复制的全局视图（见第 4 章）
状态Legacy 维护态主线增量

关键差别在引擎层参与度：Legacy DSA-CP 是 attention 后端"闷头自己切"，调度器对此无知；PCP 是 Model Runner 在 batch 分区时就切好（partition_batch），调度器、metadata、attention 全链路都知道"这个 batch 是切过的"。这就是"私搭通道"和"正道"的本质区别。

4. 同文件的三个类：一次换班的现场

最有意思的现场在 dsa_cp.py 一个文件里：Legacy 与 PCP 两代实现同文件共存、共享全部 DSA 计算内核。文件里有三个关键类，继承关系就是换班交接书：

vllm_ascend/attention/context_parallel/dsa_cp.py · L57（Legacy 标注）与 L2129-2133（PCP 版类头）
# =============================================================================
# Legacy DSA-CP implementation (TP/SP group)
# =============================================================================

class AscendDSAPCPImpl(dsa_v1.AscendDSAImpl):
    """Run batched global DSA cache updates before rank-local PCP attention."""

    supports_pcp: ClassVar[bool] = True

PCP 版的 Impl 类直接继承 Legacy 同文件的基类链（dsa_v1.AscendDSAImpl），DSA 的稀疏注意力内核、indexer、compressor 一概不动——换班换的不是计算，是"输入怎么来、缓存怎么写"的外围编排：

  • 输入侧：PCP 各 rank 拿到的是本地分片的 padded batch，attention 前先 all-gather 拼回全局、按 hidden_restore_idx 恢复调度器原序；
  • 缓存侧：SWA/compressor/indexer 三类缓存的写入用全局 slot_mapping——每个 rank 都基于全局视图写自己负责的那份复制缓存（写入前有 fence，写入后注意力读本地副本）；
  • 输出侧：_get_o_proj_input_shape 报本地行数，o_proj 只算本地段，跨 rank 合并交回引擎层。
vllm_ascend/attention/context_parallel/dsa_cp.py · L2139-2152（PCP：全局聚合还原调度序）
def _gather_and_restore_hidden_states(self, hidden_states, metadata):
    """All-gather one padded rank slice and restore scheduler token order."""
    gathered_hidden_states = get_pcp_group().all_gather(
        hidden_states.contiguous(),
        dim=0,
    )
    return torch.index_select(
        gathered_hidden_states,
        0,
        metadata.hidden_restore_idx,     # ← 恢复调度器原序（去 padding）
    )
vllm_ascend/attention/context_parallel/dsa_cp.py · L2160-2180（PCP：复制的 SWA 缓存全局更新一次）
def _update_global_swa_cache(self, layer_name, global_hidden_states, swa_kv_cache, swa_metadata):
    """Update the replicated SWA cache from the canonical global batch."""
    req_metadata = dsa_v1._require_req_metadata(swa_metadata)
    assert req_metadata.slot_mapping is not None

    kv = self.kv_norm(self.wkv(global_hidden_states))
    kv = kv.view(-1, 1, self.nope_head_dim + self.rope_head_dim)
    torch.ops._C_ascend.inplace_partial_rotary_mul(kv.unsqueeze(1), ...)
    get_dsa_attn_kv_plan(self.vllm_config).dsa_kv_compress_scatter(
        swa_kv_cache,
        kv,
        req_metadata.slot_mapping,     # ← 全局 slot_mapping：每 rank 用同一份全局视图写缓存
    )

再看引擎侧：vllm-ascend 没有重写 PCP 调度，只写了一个 218 行的壳：

vllm_ascend/worker/v2/pcp_manager.py · L24 与 L44-45（继承上游）
from vllm.v1.worker.gpu.pcp_manager import PCPManager      # ← 上游 vLLM 的 PCP 实现

@dataclass(frozen=True)
class AscendPCPAttentionContext:
    """Canonical global PCP view for one attention step."""
    global_batch: AscendInputBatch
    global_block_tables: tuple[torch.Tensor, ...]
    global_slot_mappings: torch.Tensor
    hidden_restore_idx: torch.Tensor
    local_num_tokens_after_padding: int

class AscendPCPManager(PCPManager):
    """PCP manager that refreshes Ascend-only local-batch metadata."""

AscendPCPManager 继承上游 PCPManager，只做三件昇腾特有的事：FULL decode graph 的 pad 布局对齐、slot mapping 按 rank 展开填充、给 attention metadata builders 组装全局上下文。分区的"正道部分"——怎么切、怎么合并、怎么让调度器知情——全部复用上游。

代价与边界PCP 用"缓存复制"换工程简洁：每个 PCP rank 持有全局 KV 视图的复制副本（写入去重靠全局 slot_mapping），显存开销高于 DSA-CP 的分片存储。这是设计取舍——它把复杂性交还给引擎统一调度，换取的是不再需要为每个邻居单点协商。另外 sparse MLA 场景下 PCP 暂只支持 eager 或 FULL_DECODE_ONLY 图模式。

5. 两代怎么选：互斥开关与选路代码

后端入口的选路代码只有十几行，把两代关系写得明明白白：

vllm_ascend/attention/dsa_v1.py · L110-131（get_builder_cls：入口三分支）
from vllm_ascend.utils import enable_dsa_cp

use_dsa_cp = enable_dsa_cp()
use_pcp = enable_pcp()
if use_dsa_cp and use_pcp:
    raise ValueError("Legacy DSACP and PCP cannot be enabled at the same time.")
if use_dsa_cp:
    from vllm_ascend.attention.context_parallel.dsa_cp import AscendDSACPMetadataBuilder

    return AscendDSACPMetadataBuilder          # ← Legacy DSA-CP（additional_config 开关）
if use_pcp:
    from vllm_ascend.attention.context_parallel.dsa_cp import AscendDSAPCPMetadataBuilder

    return AscendDSAPCPMetadataBuilder         # ← PCP（--prefill-context-parallel-size 开关）
return AscendDSAMetadataBuilder

同一套互斥判断在 get_impl_cls（选实现类）里再来一遍——builder 和 impl 两层都拒绝共存。enable_pcp() 读的是上游通用并行配置（prefill_context_parallel_size > 1），enable_dsa_cp() 读的是昇腾私有配置（且自动收敛到 get_ascend_config() 校验路径，模型没有 indexer 时强制回 false）。两个开关管的是同一个位置的两代人，新开关打开时必须关掉旧的。

6. 迁移清单：换 PCP 要满足什么条件

把散在各文件的校验集中成一张清单（每条都有源码行号背书）：

  • 引擎必须是 v2：v1 配 PCP 直接 ValueError（platform.py L1483）；
  • 四不开：PP>1、encoder-decoder 模型、多模态输入、LoRA（pcp_manager.py 逐项 NotImplementedError）；
  • 投机解码暂不支持（speculative_config 非空即拒）——MTP 用户暂留 Legacy；
  • 与 Legacy DSA-CP 互斥：开了 enable_dsa_cp 就不能开 PCP，反之亦然；
  • sparse MLA 图模式受限：仅 eager 或 FULL_DECODE_ONLY；
  • SP 开着时：max_num_batched_tokens 会被自动改写成 tp_size × pcp_size 的整数倍（有 warning 日志，属于自动适配非报错）。

7. 怎么理解这次换班

把三层事实叠起来看，"日落"是个准确的词：不是枪毙，是不再灌注。Legacy DSA-CP 的代码还在、开关还在、v1 用户还能用；但它标志着一条分界线——此前的 vllm-ascend 习惯"缺什么自己搭"（DSA-CP 如此，SP 直通协商也如此），此后上游把长序列 prefill 并行收编为通用能力，vllm-ascend 的正确姿势变成写薄壳对齐上游（218 行的 pcp_manager 壳对峙 2291 行的 legacy 文件，就是两种姿势的体量对比）。

对使用者的操作含义：新部署（尤其 GLM/DeepSeek 长序列 prefill 场景）优先评估 PCP 路线（v2 引擎 + --prefill-context-parallel-size），对照第 6 章清单过一遍边界；存量 v1 + DSA-CP 部署不用慌——Legacy 路径仍是当期能跑的正式路径，迁移等上游 PCP 把投机解码等边界补齐再动不迟。
