读前须知：四个名词 30 秒（更多缩写见文末第 8 章术语速查）
  • TP（张量并行）：把一层的权重/计算切到多张卡各算一块——TP=16 即 16 卡一组；
  • SP（序列并行）：TP 组内再把输入序列横向切，每卡只拿一段连续 token；
  • PP（流水线并行）：把模型的 N 层按层切成分段（stage），各段在不同卡组上接力——本 PR 的开关就卡在 PP 上；
  • FlashComm1：GLM V1 的 SP MoE 通信模式——decoder 开 SP、注意力投影不自带归约，归约交给统一收口。
一句话总结 上游 vLLM 有一个 PP=1 guard：PP>1 时一刀切关掉 decoder 级 SP（因为上游 PP transport 期望全量激活）。于是 PP>1 的 GLM V1 出现名实不符：FlashComm1 状态上报为开启，decoder SP 实际被关，o_proj 还带着每层一次的白归约。本 PR 的思路是自己兑现上游的前提：五条件选路重开 stage 内 SP、o_proj 交出归约权、把"聚回全量"上移到每个 PP 出口、Runner 的 PP 中间张量口径改成全量——上游要什么布局，边界上就还给什么布局。

2. 问题：guard 一刀切，FlashComm1 名开实关（改动前）

先理清四个角色怎么协作。TP=16 把一层切到 16 卡；SP 在 TP 组内再把 token 横切成连续段（每卡一段）；PP 再把模型的 N 层按层切成分段（stage）接力——层是 PP 的切法，token 是 SP 的切法，两者正交。GLM DSA V1 开全局 SP（FlashComm1 模式）时，decode 侧的分工是：注意力投影不自带归约，由 decoder 收口统一归约——这样每层省一次集合通信，这正是 FlashComm1 的收益来源。

但上游 vLLM 立了一条 guard：PP>1 时关掉 decoder 级 SP。原因在上游自己的传输约定——它的 PP transport 期望拿到全量激活，如果 stage 内跑 SP、出口传出的是分片，上游的接法就对不上。guard 一刀切之后，PP>1 的 GLM V1 就出现了下面的名实不符（PP 切层与 SP 的关系见图 3）：

3. 核心思路：自己兑现上游的前提

guard 的担忧是对的——上游 transport 确实只认全量。本 PR 不跟 guard 对着干，而是把 guard 的前提自己兑现：stage 内部照开 SP（拿 FlashComm1 的收益），在每个 PP 出口把 hidden/residual 聚回全量再交给 transport；o_proj 的归约权从"每层各归各的"收归 decoder 统一收口；Runner 侧所有 PP 中间张量的口径同步改成全量。一句话：边界还上游一个全量，stage 内换回真正的 FlashComm1。改后的样子见图 4：

4.3 十行示例，vllm-ascend 原本是怎么完成的

先摆出锚点代码——一份典型的 attention 推理实现，矩阵乘、RoPE、KV Cache、softmax，十来行（GQA + KV Cache 写法，batch 维省略）：

# 十行 attention 示例（推理版，等价于典型的 GQA+KVCache 教程实现）
def forward(x, is_prefill):                            # x: [1, seq, hidden]
    q = x @ wq                                         # L1  Q 投影
    k = x @ wk;  v = x @ wv                            # L2  K/V 投影
    q = rope(q, pos);  k = rope(k, pos)                # L3  RoPE，只转 Q/K
    k_cache = k if is_prefill else cat(k_cache, k)        # L4  KV Cache：整条历史拼在本卡
    v_cache = v if is_prefill else cat(v_cache, v)
    k_full = k_cache.repeat_interleave(4, dim=1)       # L5  GQA：2 组 KV 复用给 8 个 Q 头
    scores = q @ k_full.transpose(-1,-2) / sqrt(dk)    # L6  打分——隐含假设：全量历史都在本卡
    if is_prefill: scores = causal_mask(scores)        # L7  因果遮罩
    w = softmax(scores, dim=-1)                        # L8  归一化
    out = w @ v_full                                   # L9  加权求和
    return out @ wo                                    # L10 输出投影
图 7 · 流水线（原本）：十行示例在 vllm-ascend 里的完成过程（没有这次 PR 时的样子）

看懂这张图，记住三件事。

一、十行示例一步没少。左列每一行，中列都有对应——投影、RoPE、写缓存、稀疏注意力、收口，数学原样；唯一的例外是 L5（GQA repeat），MLA 系用 latent KV 全头共享达到同样目的，所以没有独立步骤。

二、实现分散在三个模块，但只有一条调用链。models/ 发起 → ops/ 放行 → attention/ 干活；右列就是每一站的地盘和门牌（文件:行号）。

三、本 PR 不碰这张图。九步流水线是"stage 内怎么算"，本 PR 管的是"层外壳的开关"与"PP 边界的布局"——往下看时序图时请带着这个分工。

4.4 全链时序：谁调用谁，每一棒先自己干再交棒

图 7 看的是"数学落在哪"。这份工作是谁发起、又一层层交给谁的？把整条调用链按时间拉开——六个类六条泳道，每个函数先标"自己干了啥"，再标"委托给谁"：

图 8 · 全链时序图：从引擎到后端，每个类"自己做什么 / 委托什么"（文件与行号本地实测）

读这张图抓三个节奏。

一、委托链只有一条，没有岔路。引擎组批 → Worker 接批 → Runner 喂料 → 层外壳发起 → 门卫放行 → 后端开算；每一棒只把活交给下一棒，谁也不越级。

二、"自己干"的都是壳上的杂活，"委托"出去的才是正餐。Worker 自己只做监控与流水线收发；Runner 自己只做 pad 和组元数据；把十行示例真正算出来的，是最右边后端的那串自转圈。

三、本 PR 动的是泳道之外的两样东西。层外壳进来的姿势（SP 开没开、o_proj 归不归约）和 PP 出口交出去的姿势（全量还是分片）——泳道内的每一棒都没变。

4.5 为什么这么实现：逐步收益

图 7 回答了"落在哪"，图 8 回答了"谁调用谁"，还剩最后一个问题：每一步为什么这么实现？各自省的是什么？把图 7 中列的流水线原样搬到最左列，向右逐层展开——怎么做（带门牌）→ 为什么这么设计 → 收益点：

图 9 · 昇腾实现展开图：最左列 = 图 7 中列流水线；向右逐层展开「怎么做 → 为什么 → 收益点」

逐行看收益，"省"分三种，省的东西不一样。

省显存的：低秩 latent 让 KV Cache 不随头数翻倍；slot 页表定位省掉整块 cat 的大拷贝。

省带宽的：融合算子让中间结果不落显存——投影+rmsnorm+rope+写缓存一个算子，QKᵀ→softmax→·V 一个算子。

省算力的：稀疏注意力只算 indexer 选中的 top-2048 块，不扫全量历史；序列越长，省得越多。

而本 PR 要省的，是这张图之外的一次通信：FlashComm1 语义下 o_proj 本可以不归约（每层省一次集合通信）——PP>1 时被 guard 一刀切关掉。九步数学没变，变的是开关。

4.6 问题：PP>1 时，SP 被 guard 关掉了

图 10 · 改前户口：模块 → 类 → 方法（patch_deepseek_v2.py 的 _patched_forward，层 SP 关、Ⓐ 白归约）

把问题钉在代码上。上游的 guard 长在层外壳的组装处：PP>1 时 use_sequence_parallel_moe 不会被置真，decoder SP 整段关闭；而 o_proj 是 RowParallelLinear，reduce_results=True 意味着每层投影后各自做一次归约——这在与 FlashComm1 语义（归约收归 decoder 统一做）组合时就是纯白做：

# 改前状态（上游 guard 生效时，有删节）
layer.use_sequence_parallel_moe = False        # Ⓑ guard：PP>1 时 decoder SP 被关
layer.self_attn.o_proj.reduce_results = True   # Ⓐ 每层投影后各归各的——白付一次集合通信
# 而配置侧 FlashComm1 仍是"开启"——名实不符就从这来

更隐蔽的是这份"名实不符"的迷惑性：看配置、看日志，FlashComm1 都像是在跑；只有对照层外壳才知道 SP 没开、归约白付。问题不在十行数学，在开关与它背后的前提。

4.7 这次 PR：五条件重开 SP，边界还上游一个全量

图 11 · 改后户口：模型 init 补丁五条件选路（patch_deepseek_v2.py :326 起），层 SP 重开、o_proj 交出归约权

PR 的三处源码改动，一句话一个：

# PR 新增（patch_deepseek_v2.py :326，有删节）：模型 init 补丁里的选路函数
def _enable_glm_pp_sequence_parallel(self, vllm_config) -> None:
    # 上游在 PP 下关 decoder SP，因为 transport 期望全量——
    # 本补丁的 forward 会在每个 PP 出口恢复全量，所以这里敢开
    if vllm_config.use_v2_model_runner:
        return                                     # 条件1：仅 V1 runner
    parallel_config = vllm_config.parallel_config
    if (vllm_config.model_config.hf_text_config.model_type != "glm_moe_dsa"
            or getattr(vllm_config.model_config.hf_text_config, "moe_layer_freq", 1) != 1
            or parallel_config.pipeline_parallel_size <= 1
            or not parallel_config.use_sequence_parallel_moe):
        return                                     # 条件2~5：GLM DSA / 层频=1 / PP>1 / SP 开
    for layer in islice(self.layers, self.start_layer, self.end_layer):
        if isinstance(layer.mlp, DeepseekV2MoE) and isinstance(layer.self_attn, DeepseekV2MLAAttention):
            layer.use_sequence_parallel_moe = True       # 重开 stage 内 SP（dense 层不动）
            layer.self_attn.o_proj.reduce_results = False  # 交出归约权：同一投影对象被 MLA 后端持有

6. 与我们排查问题的关系

如实说：这个 PR 不直接打我们的场景 我们环境是双 A3、TP=16 DP=2、PP=1——guard 的条件（PP>1）在我们这根本不触发，所以 18671 的 DSA-CP 优化也不受本 PR 影响（它明确声明不动 #18671）。但它是同一套布局契约体系的 PP 维度补全：18671 解决"PP=1 时聚了又切"，18870 解决"PP>1 时 SP 被 guard 关掉"。将来若多机切 PP（stage 接力），这个 PR 就是 FlashComm1 能开的前提。

方法论上值得记一笔：guard 的约束（transport 期望全量）是对的，错的是一刀切的实现。本 PR 的解法不是绕过约束，而是把约束的前提自己兑现——"边界还全量，stage 内才敢开 SP"。这个模式和 18671 的"布局契约"一脉相承：与其让开关一刀切，不如把布局责任钉在边界上。

PR 自述状态：ruff 通过；选路矩阵与口径匹配的回归用例已就位；张量单测与 NPU 正确性/性能验证仍 pending，此前一轮 CI 败在环境（pip 证书与 apt 签名），还没跑到测试。

7. 收益、风险与待验证

收益 PP>1 的 GLM DSA V1 部署真正拿到 FlashComm1：decoder SP 生效、Ⓐ 每层白归约消失、归约收归统一收口。无需新配置项——条件满足自动生效。
安全性设计 五条件与门 + 层级 isinstance 双查：模型/runner/PP/SP 任一不满足即整段返回，行为与改前一致；dense 前缀层不动；交错 dense/MoE 不动；#18671 的 DSA-CP 优化明确不变。
待验证（PR 自述） 张量单测未跑完；NPU 正确性与性能验证 pending；无性能数据（作者明说"No performance gain has been measured"）；前轮 CI 败在环境未到测试。当前开放中、以合入版为准。
对我们的行动建议
  • 现在不动：我们 PP=1，本 PR 行为对我们无变化；
  • 跟进 CI 与 NPU 验证结论——若合入，它验证了"patch 层重开 SP + 边界还全量"这套模式的可行性，与 18671 是同一张蓝图的两块；
  • 若将来上 PP（stage 接力），回看本篇第 4.7/5.2：出口聚全量是 FlashComm1 的前提。
