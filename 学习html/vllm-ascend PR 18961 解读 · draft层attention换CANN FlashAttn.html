2. 问题：draft 层的 attention 借了别人的引擎（改动前）

GLM 的架构（①）里除了 N 层主模型，还有一件 MTP 模块——前两篇讲布局时它一直在图角落里挂着黄框。这次它当主角：推理时 draft 先连猜 k 个 token，主模型一次前向验证（一轮"猜-验"见下图 3 上半部）。draft 层自己也是一层层 Transformer，每层也有 attention——数学与主模型一字不差；差别全在"被调用的方式"：序列极短、每步 k 次连猜、验证淘汰后下一步重来。

进了框架，每层的 attention 都要由框架配引擎（③的 platform.py 管这件事）。主模型 target 顺利选上 SFA（稀疏注意力后端）；draft 层呢——它查的是同一张选路表，而表里它的特征是"非 MLA、非稀疏、非压缩"，落格到通用 attention 后端，与最普通的 dense 层同桌吃饭（Ⓐ）。通用后端为"大而全"设计：每层各自建注意力元数据、长度依赖 CPU 镜像——拒绝采样刚淘汰过 token，CPU 镜像可能还没同步；每个 draft step 的每层还要各自重建 tiling 计划，一步 k 次猜 × N' 层，备料重复 N'×(k+1) 次（Ⓑ）。这些开销全部吃进每 token 时延：上游 #18717 两节点 P/D 实测，mean TPOT 14.90 ms 里相当一块是备料，不是数学。

图 2 · 改动前：Ⓐ draft 与 dense 同表选路，Ⓑ 备料逐层重复——TPOT 的大头不在数学在备料
图 3 · target 与 draft 的分工：一轮「猜-验」循环里，draft 的 attention 跑 k 次、备料也随之重复 k 次

ⒶⒷ 速查（后文正文与代码注释均用此编号）

  • Ⓐ 选路同表：draft 层的 attention 与最普通的 dense 层查同一张 backend_map 选路表，落格到通用后端（attention_v1）——没有 draft 专用路径；
  • Ⓑ 备料重复：每层各自建注意力元数据、长度依赖 CPU 镜像（拒绝采样后可能过期）、每层各自重建 tiling 计划——一步 k 次猜 × N' 层，重复 N'×(k+1) 次。

3. 核心思路：窄门换引擎，target 不动

问题住在引擎与备料上，数学没病——那就不动数学，换引擎。本 PR 三条思路：一、新后端：attention/fa_v1.py 三件套（元数据从 device 长度建、tiling 计划按几何特征缓存并在一个 draft step 内层间复用、CANN flash_attn 算子出结果后回填 vLLM 的输出缓冲）；二、窄门：只在七重条件全过时启用——A5 硬件、V1 runner、本层是 draft、draft 必须 eager、target 是 glm_moe_dsa、draft 是 DFlash2、FP16/BF16 未量化 KV（另排除五个未实现的特性），任一不满足静默回老路，行为与改前一致；三、target 不动：主模型照旧选 SFA，"缓存的 target 选路不变"有测试钉死。改后的样子见图 4：

4.1 先看这块推理的原始写法：朴素 PyTorch

老规矩，先立对比基准——这块推理（draft 层的投机解码一步）用 PyTorch 朴素写出来长什么样。自己动手写带草稿模型的推理就会这么写：单卡、没有任何框架概念（有删节）。draft 层的 attention 数学就在 layer 里，与主模型一字不差：

# 朴素 PyTorch 写法：投机解码的一步（单卡，无框架）
draft_kv = []                                 # draft 层自己的 KV 缓存
for t in range(k):                            # draft 连猜 k 个 token
    x = embed(last_token)
    for layer in draft_layers:                # draft 模型的 N' 层
        h = layer.self_attn(layer.norm(x), cache=draft_kv)
        # attention：QKV 投影 → QKᵀ → softmax → ·V → o_proj
        h = layer.moe(h)                      # 前馈；GLM 这层是 MoE
        x = h + x                             # 残差
    last_token = lm_head(x).argmax()          # 猜出下一个 token

accepted = verify(draft_tokens)               # 主模型一次前向，验证 k 个猜的
# 收下命中的、淘汰没中的，下一轮 decode 循环重来

这次 PR 动的不是这段数学——数学一行没动。动的是 vLLM 框架给这段朴素代码加的壳：进了框架，每层的 attention 要由框架配引擎——选哪个后端（Ⓐ）、配料怎么备（Ⓑ：元数据/长度/tiling 计划）。裸 PyTorch 里根本没有"配引擎"这件事，attention 就是 layer 里那几行；draft 层被调用方式的特殊（每步 k 次、序列短、每步重来），框架的老壳没有为它定制——问题全住在壳上（ⒶⒷ 代码长相见第 2 章）。

4.5 为什么这么实现：逐步收益

还剩最后一个问题：target 这条路每一步为什么这么实现？各自省的是什么？把流水线中列原样搬到最左，向右逐层展开——怎么做（带门牌）→ 为什么这么设计 → 收益点：

图 9 · 昇腾实现展开图：最左列 = 图 7 中列流水线；向右逐层展开「怎么做 → 为什么 → 收益点」

逐行看收益，"省"分三种。省显存的：低秩 latent 让 KV Cache 不随头数翻倍；省带宽的：融合算子让中间结果不落显存；省算力的：稀疏注意力只算选中的块。本 PR 省的是第四种——省备料：不算得更快，是"准备算"更快（device 长度一次取齐、tiling 计划一步一建），这是 TPOT 那 26% 的来源。

新后端三件套各自干了什么（fa_v1.py，关系化拆解）：

  • 元数据件（Builder）：干了什么——从 device 侧精确长度建注意力元数据；跟 draft 什么关系——拒绝采样刚淘汰 token，CPU 镜像可能还没同步，draft 每步都踩这个坑，所以只信 device；省什么——算错窗口重来的返工；
  • 计划件（plan 缓存）：干了什么——tiling 计划按几何特征（头数/KV 头数/head_dim/窗口/布局）做 key 缓存在元数据里；跟 draft 什么关系——一步 k 次猜 × N' 层的调用里，同几何的层共用一份计划；省什么——host 侧重建计划的纯开销，TPOT 那 26% 的主力；
  • 算子件（Impl）：干了什么——在 KV 传输窗口内调 CANN flash_attn，结果 copy_ 回 vLLM 的输出缓冲；跟朴素代码什么关系——就是十行示例那几行数学的 CANN 融合版；省什么——融合算子中间结果不落显存（省带宽），且只在用到它的 worker 里 import CANN。

5.2 新后端核心：备料一次，层间复用（fa_v1.py）

# fa_v1.py · AscendFlashAttentionImpl.forward_impl（有删节）
# 只在用这个后端的 worker 里才 import CANN——别的部署不多背一个依赖
from cann_ops_transformer.ops import flash_attn, flash_attn_metadata

# Ⓑ 反面一：长度只信 device，惰性算一次，存在 metadata 里
if metadata.flash_attn_lengths is None:
    boundaries = metadata.query_start_loc_gpu[: num_reqs + 1].int()
    boundaries = boundaries.clamp(min=0, max=query.shape[0]).cummax(dim=0).values  # dummy 请求可能有重复/负边界
    lengths = metadata.seq_lens_gpu[:num_reqs].int().clamp(min=1)
    metadata.flash_attn_lengths = boundaries, lengths

# Ⓑ 反面二：tiling 计划按几何特征做 key，一个 draft step 内层间复用
plan_key = (self.num_heads, self.num_kv_heads, query.shape[-1], self.sliding_window, layout_kv)
cached = metadata.flash_attn_plans.get(plan_key)
if cached is None:
    attrs = dict(... mask_mode=4 if ... else 3 if metadata.causal else 0,   # 0 无遮罩/3 因果/4 滑窗
                 layout_q="TND", layout_kv=layout_kv, layout_out="TND")
    cached = flash_attn_metadata(...), attrs
    metadata.flash_attn_plans[plan_key] = cached

with attention_transfer_window():          # KV 池传输窗口内调用
    result, _ = flash_attn(query, self.key_cache, self.value_cache,
                           block_table=..., metadata=plan, **attrs)
    output[: query.shape[0]].copy_(result)  # CANN 返回新张量；vLLM 要自己的输出缓冲——回填
    return output

三个细节值得停一下：clamp+cummax——dummy 请求的边界可能重复甚至为负，不做这两步会算出非法窗口；plan_key 五元组——同几何才共享，换头数/换窗口自动分家（"不同几何不共享 plan"有测试）；copy_ 回填——CANN 的返回是新张量，vLLM 的约定是写进它给的缓冲，一行 copy_ 把两个约定接上。

6. 与我们排查问题的关系

  • 硬件对上了：门槛条件二的 A5（950DT）就是《Profiling 实战解读》那台机器——本 PR 合入并升 CANN 9.2 后，我们环境里 GLM 家族 + draft + eager 的组合直接受益；
  • TPOT 拆解多了一个怀疑对象：以前拆每 token 时延，眼睛盯着算子耗时（ DispatchFFNCombine 那类）；这个 PR 提醒还有第四种账——备料（host 侧建元数据/建计划的纯开销）。用姊妹篇的三板斧能直接看：draft 窗口的 op_statistic 里 host 侧 API 计数掉没掉；
  • eager 不再等于慢：排查时切 enforce_eager 复测是常用手段，以前要付出"draft 变慢"的代价——这条 PR 把代价摘了，手段更干净；
  • "参数生效了吗"多了一个样本：换引擎属于「换实现」类改动（四分类里的第一类），验证就是 diff op_statistic——draft 的 attention kernel 名换成 CANN FlashAttn 一族即生效（《算子与 vLLM 参数》1 节四分类的实战案例）；
  • 家族延续：#18671 拆布局（PP=1）、#18870 补边界（PP>1）、本篇换引擎（draft）——同一条 GLM 部署线的第三块拼图。

7. 收益、风险与待验证

收益 上游 #18717 两节点 P/D 实测：mean TPOT 14.90 → 10.97 ms（约 −26%），output throughput 484.39 → 491.31 tok/s——省的是备料不是数学。950DT + CANN 9.2 上 16 个 eager 精度用例全过（FP16/BF16、strided paged KV、causal/non-causal、滑窗、rejection 后长度）。
安全性设计 窄门七重条件 + 静默回退：任一不满足行为与改前一致；target 选路有测试钉死；不同几何不共享 plan；CANN 只在用到它的 worker 里 import。
待验证（PR 自述） 性能数字出自 #18717 原始修订，本回移植未重新压测；依赖 CANN 9.2 与 A5 能力位；条件不满足是静默回退——不主动验证就会"以为换了其实没换"。PR 开放中，以合入版为准。
对我们的行动建议
  • 跟进合入；合入后在 A5 + CANN 9.2 环境用真实 GLM/DFlash2 配置跑一遍 4.10 的选路单测，确认窄门开；
  • 按《算子与 vLLM 参数》三板斧验生效：diff 前后 op_statistic，draft 的 attention kernel 应换成 CANN FlashAttn 一族；
  • 再压一轮 TPOT 对比 10.97 ms 这条线——回移植版本值得有自己的数字。

术语本 PR 语境下的含义
target / draft主模型与它的草稿小模型（①的 MTP 模块）：draft 连猜 k 个 token，target 一次前向验证
