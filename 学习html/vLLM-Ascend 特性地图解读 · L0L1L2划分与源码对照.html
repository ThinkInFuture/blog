两条线的划分依据是代码变更的驱动方：模型特性的变更由 GLM 模型结构升级驱动 （如 SFA 相关文件位于平台层，但由 GLM 稀疏注意力结构驱动，仍属模型特性线）； 框架特性的变更由 vLLM 上游演进驱动（如 cache_config.py 的 C8 派生逻辑对所有模型生效， 属框架特性线）。投机解码等跨界特性按子项拆分：方法框架属框架特性线，GLM 的 MTP 头适配属模型特性线。

② 典型特性：先讲清楚是什么，再拆功能链定归属

这一节怎么读：挑三个典型特性（DP / EPLB / chunkPrefill），每个用三张图讲透：一张讲它是什么，一张看它在实测环境里的样子/效果，一张把工作链逐点拆开（蓝框★ = GLM 适配点）——蓝框★ = GLM 适配点（必须按 GLM 结构实现，换模型即失效），灰框 = GLM 无需适配的功能点（右列逐点给出原因）。链上有没有适配点，就是 L0 归属的判断依据。

特性一：DP（数据并行）——先说它是什么

DP（Data Parallelism，数据并行）就是把整套模型复制多份，每份叫一个 DP 实例，各处理各的请求：新请求到来时由负载均衡（DPLB）分给最闲的实例，实例之间互不干扰，吞吐量跟着实例数涨。实测环境 TP=16、DP=4，就是 4 份完整的 16 卡副本同时服务。注意 DP 本身不切模型、只切请求——真正要按模型结构动刀的，是每个实例内部的层内切分与通信插入（下面功能链里带 ★ 的三步）。所以「DP 归哪条线」不是一句话能答的，得拆开看每个功能点。

特性二：EPLB（专家负载均衡）——先说它是什么

MoE 模型的专家是路由制：每个 token 只去少数几个专家，于是天然不均——热门专家被挤爆、所在卡算力打满，冷门专家闲着，整卡的吞吐被最忙的一张卡拖住。EPLB（Expert Parallelism Load Balancer，专家负载均衡）干三件事：每 600 步统计一次各专家的 token 路由热度 → 按热度给过热专家复制冗余副本、重新摆放到空闲卡（专家权重 NPU 间 D2D 直接搬移）→ 对上层模型接口零改动，配置只有 eplb_config 一个入口。它只看负载统计、不看模型结构——这个特点决定了它的归属。

特性三：chunkPrefill（长输入切块预填充）——先说它是什么

一个 3500 token 的长 prompt，如果 prefill 一口气算完，这几百毫秒里整卡都被它占住，同批的 decode 请求全部干等——长请求的 TTFT 没快，别人的 TPOT 却被拖爆。chunkPrefill（长输入切块预填充）把长输入按固定块大小切块（如 1024，由 profiling_chunk_config 配置），一次前向只算一块：块 1 算完写 KV 就让出算力，下一轮调度再算块 2，拿着块 1 的 KV 续算，注意力跨块连续。长请求被摊进多个调度轮，decode 不再被长 prompt 卡死。它处理的对象只有「请求与块」，不接触模型结构。

⑥ GLM 视角：重点关注的格子

结合 GLM 系模型的结构特性（KDA 注意力 / 稀疏索引 / MLA / MoE / 1M 上下文），特性表里 与 GLM 强相关的重点格（也是精度与性能问题的高发区域）：

  • 量化加速 → attention+indexer（GLM-5.1 的 sfa_c8/li_c8——精度案核心开关，params-04/precision-rca）；
  • 融合算子 → attention（MLAPO/qknorm_rope——GLM 前处理热点，params-03）；
  • multi stream → moe 双流（GLM MoE 的共享专家与路由并行，params-02）；
  • 并行切分 → 细粒度 TP（GLM-5.1-198k 的 lmhead/oproj 切分组合，params-05）；
  • 投机解码 → mtp/dspark（GLM 下一代配合 DSpark 的动态步数，params-07）；
  • 精度一致性（RL 训练一致性开关——GLM RL 阶段的保底工具，params-08）。
