1、大模型推理流程

自回归大模型通用推理流程，不绑定GGUF、不绑定vLLM，权重文件只参与模型加载步骤。

flowchart TD A["磁盘模型文件"] --> B["模型加载"] B --> C["Prompt输入"] C --> D["Tokenizer编码"] D --> E["Transformer前向计算"] E --> F["输出Logits"] F --> G["采样下一个Token"] G --> H{"停止条件"} H --否--> I["更新KV‑Cache"] I --> E H --是--> J["解码输出文本"]

流程关键点位说明

  1. 模型加载：唯一读取磁盘权重文件的环节。如果文件是GGUF：读取头部、元数据、张量索引、量化类型qtype、量化权重二进制；将权重映射/拷贝进内存显存。
  2. Tokenizer编码：Tokenizer从GGUF元数据读出到内存，不再读磁盘。
  3. Transformer前向计算【量化反量化发生点】：不再访问GGUF磁盘。算子读取内存中已经加载的量化权重，依靠内存保存的qtype信息做实时反量化，执行矩阵乘法。
  4. 采样、KV‑Cache、解码：全部运行在内存，和GGUF磁盘文件无交互。

2、推理流程和 GGUF 的关系

第一层：抽象推理两阶段（不区分llama.cpp/vLLM）

flowchart TD A["GGUF磁盘文件"] --> B["阶段A：模型加载（仅一次IO）"] B --> C["阶段B：推理循环（反复计算）"]

阶段A：模型加载——从GGUF磁盘读取哪些东西

  • Header：校验GGUF文件合法性。
  • Metadata：模型架构、层数、上下文窗口、Tokenizer二进制。引擎用它初始化模型对象。
  • TensorInfo张量索引：权重名称、维度、量化类型 qtype、该权重在GGUF文件内字节offset偏移。
    • offset：告诉引擎到磁盘哪个字节位置读取权重二进制；
    • qtype：记录权重压缩格式（Q4_K_M/Q8_0），推理反量化的依据，加载后存入内存。
  • 权重二进制字节：量化后的原始数据，映射或者拷贝进入内存/显存。

阶段B：推理循环——GGUF磁盘文件完全退出

  • 磁盘GGUF文件可以关闭，不再发生磁盘IO；
  • 所有权重、qtype标记、Tokenizer全部驻留内存/显存；
  • 前向计算时，算子读取内存的qtype，调用对应反量化函数，把压缩权重还原为浮点参与矩阵运算。
通俗例子：GGUF是磁盘上的压缩包。阶段A：打开压缩包，读取目录清单（元数据+张量索引），把压缩数据载入内存，记住每个文件的压缩格式(qtype)。阶段B：直接操作内存内压缩数据，现场解压运算，不会重复打开磁盘压缩包。

3、GGUF详解 — llama.cpp和GGUF协同，gguf里面都有啥

GGUF是静态二进制存储格式，本身不具备任何计算能力；全部反量化、矩阵运算、推理逻辑由llama.cpp/vLLM这类引擎实现。下面列出GGUF内部每一块内容，并且明确每一块在推理流程中承担的角色。

3.1 GGUF文件物理布局流程图

flowchart TD H["Header头部"] M["Metadata元数据"] TI["TensorInfo张量索引"] PAD["Padding对齐填充"] DATA["张量权重二进制"] H --> M --> TI --> PAD --> DATA

GGUF内部各个模块与推理的对应关系

  • Header头部：魔数、版本号、张量总数、元数据总数；仅加载阶段使用，校验文件是不是合法GGUF；推理循环不再使用。
  • Metadata元数据：键‑值对，架构、层数、上下文、Tokenizer二进制；加载阶段读取，推理阶段用来构建网络、编码、解码token。
  • TensorInfo张量索引【量化核心】：权重名字、维度、qtype量化类型、文件offset偏移；加载阶段定位权重位置，把qtype拷贝进内存；推理前向计算算子依靠内存qtype执行反量化。
  • Padding对齐填充：字节对齐；适配SIMD硬件指令，提升推理矩阵运算性能。
  • 张量权重二进制：已经压缩量化后的原始字节；加载阶段读入内存/显存；推理做矩阵乘法真正运算的数据本体。

3.4 TensorInfo张量索引结构体（量化核心）

typedef struct {
    gguf_string_t name;     // 权重名字，如 blk.0.attn_q.weight
    gguf_quant_type type;   // qtype：Q4_K_M / Q8_0 / FP16，反量化的依据
    uint32_t n_dims;        // 张量维度数目

重点说明：GGUF只记录type(qtype)这个标记，不会做反量化解压。引擎加载时把type读到内存；推理算子读取内存的type，调用对应的反量化内核完成解压计算。offset用来定位磁盘上权重字节的位置。

3.6 llama.cpp 与 GGUF完整协同全链路

  1. 磁盘GGUF文件保存：Header、Metadata、TensorInfo（qtype+offset）、Padding、量化权重二进制。
  2. llama.cpp【加载阶段】：打开GGUF磁盘；读取头部校验；读取元数据构建模型参数；读取TensorInfo拿到每个权重offset和qtype；mmap映射权重字节；将qtype、维度等全部保存到运行时内存；GGUF磁盘文件可以关闭。
  3. llama.cpp【推理循环阶段】：不再访问GGUF磁盘；Transformer算子读取内存内量化权重，依据内存保存的qtype调用对应反量化内核，完成矩阵计算；Tokenizer、KV‑Cache、采样全部属于llama.cpp内部逻辑。

3.7 Python极简读取GGUF头部和张量数量示例

import struct

def read_gguf_header(path):
    with open(path,"rb") as f:
        magic = f.read(4)
        version = struct.unpack("<I", f.read(4))[0]
        n_tensors = struct.unpack("<Q", f.read(8))[0]
        n_meta = struct.unpack("<Q", f.read(8))[0]
    print(f"magic:{magic}, ver:{version}, tensors:{n_tensors}, meta:{n_meta}")

4、Bonsai-27B 定制分析与量化洞察

前 3 章讲清楚了 GGUF 是通用容器协议, llama.cpp 是通用推理引擎; 但 Bonsai 是个不通用的模型 — 它必须拉 llama.cpp 的分支 (prism) 才能跑。这一章讲: 标准 GGUF 量化 (PTQ) 为何不够用, Bonsai 拉分支的 4 个定制点是什么, 每个定制点按 场景 → 说明 → 流程 → 源码 四件套讲。

核心认知: llama.cpp 上游 main 里的 42 种 ggml_type, 绝大多数是 PTQ (训练后量化), 拿 FP16 模型 + 几百条校准集就能量化, 不需要重训。Bonsai 必须重训 (QAT + 蒸馏), 所以必须拉分支 — 这是 GGUF 量化的"训练友好型"和"PTQ 友好型"两类方法的根本分歧。

4.3 定制点 ①: 三值怎么还原 (核心定制)

场景: 为什么需要"特征还原"

GGUF 存储的是量化后的字节流, 不是 FP32 权重。推理算子 (gemm) 只能对 FP32 计算, 所以必须在算之前把量化字节 还原 成 FP32, 才能进入 Linear 层。

朴素做法: 把每个 weight 都存成 FP32, 27B 模型就是 54 GB。Bonsai 三值做法: 存成 {-1, 0, +1} + 一个 FP16 scale, 256 weights 占 66 字节 (vs FP32 1024 字节, 省 15×)。

说明: 三值的 2-bit 编码设计

每个 weight 需要 2 bit, 4 种编码:

2-bit 编码还原符号出现频率含义
00-1~25%负权
010~40-50%稀疏! 后续点积直接跳过
10+1~25%正权
11(保留)0%故意不用 — 只用 3 种编码,留 1 个未来扩展

为什么需要 FP16 scale? 如果只用 {-1, 0, +1} (绝对值都是 1), 模型表达能力太弱 (相当于 binary sign), 只能存"哪些连接重要/不重要"。加上 per-group FP16 scale, 让 {-1, 0, +1} 乘以一个动态范围, 就能表达"这个 group 里权重绝对值大" — 这是 LLM 0.1% outlier 通道的关键。

源码: dequantize_row_q2_0 (CPU 通用反量化路径)

代码位置: llama.cpp-prism/ggml/src/ggml-quants.c:439-457 
void dequantize_row_q2_0(const block_q2_0 * x, float * y, int64_t k) {
    static const int qk = QK2_0;   // blck_size = 256
    const int nb = k / qk;          // k 个 weight 分成 nb 个 block

    for (int i = 0; i < nb; i++) {
        // 1. 读 FP16 scale, 转 FP32
        const float d = GGML_FP16_TO_FP32(x[i].d);

        // 2. 遍历 block 内 256 个 weight
        for (int j = 0; j < qk; ++j) {
            // 3. 计算这个 weight 在 packed 字节流里的位置
            //    每 4 个 weight 共享 1 byte (各占 2 bit)
            const int byte_index = j / 4;
            const int bit_offset = (j % 4) * 2;

            // 4. 提取 2-bit 编码
            const uint8_t q = (x[i].qs[byte_index] >> bit_offset) & 0x03;

            // 5. 查表 + 乘 scale (00=-1, 01=0, 10=+1, 11=+2)
            y[i*qk + j] = ((int)q - 1) * d;
        }
    }
}

解读:

  • qk = 256: block 内含 256 个 weight, 这是 blck_size 字段
  • x[i].d: 这个 block 共享的 FP16 scale, 所有 weight 还原时都用同一个 d
  • j / 4: 每 4 个 weight 共享 1 byte (4×2bit = 8bit = 1B)
  • (j % 4) * 2: 这个 weight 在 byte 内的位偏移 (0/2/4/6)
  • & 0x03: 提取低 2 bit, 得到 0~3 的编码
  • (int)q - 1: 编码 0→-1, 1→0, 2→+1, 3→+2 (注意 11=+2, 跟上面"保留"的说法略有差异, 但效果一致)
  • * d: 乘以 group scale, 还原 FP32 实际值

洞察 ①.1: 三值编码设计的关键是稀疏性

为什么选 {-1, 0, +1} 而不是 {-2, -1, 0, +1, +2}?
三值 (2.0625 bpw) 比四值 (2.0 bpw) bit 多, 但 多出来的 0 值天然稀疏 — 实测 LLM 权重 ~40% 是 0, 这些 0 在点积时直接跳过, 速度反而更快。
反直觉: bit 多一点 → 更快。

洞察 ①.2: GGUF 文件合法 ≠ 引擎能跑

GGUF 文件格式允许私有 type id, Bonsai Q2_0 的 GGUF 文件本身合法。但 推理引擎必须实现 dequantize + vec_dot 才能跑。所以下游引擎不实现 Q2_0 case, 就只能看不能跑 — "unsupported tensor type Q2_0"。

4.4 定制点 ②: 点积怎么算 (CPU / GPU 不同路径)

场景: 反量化完不是终点

dequantize_row_q2_0 把 256 个 weight 还原成 FP32, 但这只是 准备数据。真正的算子是 点积: Y = sum(w[i] * x[i]), 256 次乘加。如果用朴素 FP32 算, 跟没量化一样慢 (甚至更慢, 因为多了一次反量化)。

真正的优化: 跳过反量化, 直接算 packed × Q8_1 点积。

说明: vec_dot_q2_0_q8_1 的数学

输入:

  • W: Q2_0 packed 字节流 (2-bit 三值, 无 d)
  • X: Q8_1 量化激活 (int8, 有 per-block scale)
  • 输出: dot product FP32

公式:

dot = d_w * Σ_i (q_w[i] - 1) * q_x[i]
    = d_w * [ Σ_i q_w[i] * q_x[i] - Σ_i q_x[i] ]

关键: Σ_i q_x[i] 是 activation 的总和, 可以预计算 (扫一次 X 即可)。剩下要算的就是 Σ_i q_w[i] * q_x[i]。

// Device 内联函数, 一个 warp 处理 32 个 vocab 中的一个 chunk
static __device__ __forceinline__ float vec_dot_q2_0_q8_1(
    const void * vbq, const block_q8_1 * bq8_1, const int & kbx, const int & iqs) {

    const block_q2_0 * bq2_0 = (const block_q2_0 *) vbq + kbx;

    const float     d2 = bq2_0->d;  // FP16 scale
    const int16_t * qs = (const int16_t *) bq2_0->qs + iqs * 4;  // 每次取 4 个 int16 (8 个 weight × 4 个 chunk)
    const block_q8_1 * bq8_1_chunk = bq8_1 + iqs;

    int sumi = 0;
#pragma unroll
    for (int j = 0; j < 4; ++j) {
        const int q  = qs[j];   // 一个 int16 含 4 个 2-bit 编码
        const int u  = get_int_b4(bq8_1_chunk->qs, j*2+0);  // 4 个 int8 activation 之一
        const int v  = get_int_b4(bq8_1_chunk->qs, j*2+1);  // 4 个 int8 activation 之二

        // 关键魔法: 0x020100FF 字节序列 = {-1, 0, 1, 2}
        // 用 __byte_perm 一次 SIMD 把 4 个 2-bit 编码查表还原成 4 个字节
        const int qe = __byte_perm(0x020100FF, 0x020100FF, q >> 0);  // 低 2 位查表
        const int qo = __byte_perm(0x020100FF, 0x020100FF, q >> 2);  // 次低 2 位查表

        // 把 qe/qo 重新排列成 qx (低 4 个) / qy (高 4 个)
        const int qx = __byte_perm(qe, qo, 0x5140);
        const int qy = __byte_perm(qe, qo, 0x7362);

        // dp4a: 4 个 int8 dot product, 输出 int32, 一次算完
        sumi = ggml_cuda_dp4a(u, qx, sumi);  // dot product accumulate 4×4 int8
        sumi = ggml_cuda_dp4a(v, qy, sumi);
    }
    return d2 * __low2float(sumi);  // 标量乘 d, 转 FP32
}

解读 4 个关键点:

  1. 0x020100FF 字节序列 = {-1, 0, 1, 2}: 这是个查表, 字节索引 = 2-bit 编码, 值 = 还原符号。这样 不需要分支 就能把 2-bit 编码转成符号
  2. __byte_perm: CUDA SIMD 指令, 一次把 4 个字节按位重排, 等价于 4 个并行查表
  3. dp4a: int8 dot product accumulate, 4×4 = 16 个乘加一次 SIMD 算完
  4. #pragma unroll: 让编译器展开循环, 4 次 dp4a 全部并行

4.5 定制点 ③: DSpark 投机解码

场景: 大模型生成慢在哪

27B 即使 1-bit 也要 ~6ms/步, 生成 1000 token ≈ 6 秒。这是 自回归 的代价 — 每生成一个 token 都要跑一次完整 forward。

DSpark 用一个 极小 drafter 一次性生成 K 个候选 token, 主模型 1 次 forward 验证整块, 接受 m 个 (m 接近 K 时加速 ≈ K/m 倍)。

说明: EAGLE-style block-diffusion drafter

  • 小 transformer, 接受 target 的 last_hidden_state + token embeddings
  • 每次 forward 输出 K 个 draft token
  • 用 block-diffusion 机制 (类似 mask-predict), 逐步填充 K-1 个 mask
  • confidence_head: 判断每个 draft 的质量, 决定是否继续
  • markov_head (可选): 对 draft 重采样, CUDA 加速

4.6 定制点 ④: 端到端低比特 (no escape hatches)

场景: 传统 PTQ 的"逃生通道"

大多数 PTQ 方案 (GPTQ/AWQ/SmoothQuant) 都会保留 部分层在 FP16:

  • embedding / LM head (占参数 30%+): 量化损失大, 保留 FP16
  • 前几层 / 后几层: 保留 FP16 兜底

结果: Q4_K 看起来 18 GB, 实际能砍到 ~12 GB, 但还有 ~6 GB 浪费在 FP16 部分。

说明: Bonsai 的激进做法

Bonsai 公告: "low-bit representation runs end to end across the language network, embeddings, attention, MLPs, and the LM head, with no higher-precision escape hatches"。
翻译: embedding/LM head 也量化, 一个 FP16 都不留。

为什么能这么做

  • embedding/LM head 矩阵各 ~780 MB (FP16), 量化到 1-bit 各 ~95 MB, 净省 ~1.4 GB
  • softmax over vocab 抗噪: 即使 embedding 有 1~2% 误差, 经过 softmax 后被 vocab 维度稀释, 输出 token 几乎不受影响
  • 3.9 GB 能塞进 iPhone 17 Pro (6 GB app 预算) 的关键

4.7 5 个核心洞察汇总

洞察 1: 标准 PTQ 做不出 1.7 bits 95% 精度
必须 QAT + 蒸馏 + per-group scale 三件套同时使用, 缺一不可。单独用任一个都会让 1-bit/ternary 精度崩塌到 50% 以下。
洞察 2: per-group FP16 scale 是 outlier 容忍度的关键
LLM 权重有 0.1%~1% 的 outlier 通道, 绝对值大 10~100×。per-tensor scale 被 outlier 拉高 → 其他 99.9% 权重精度只剩 0.05%。per-group scale 让每 128~256 个权重自己找 max, 精度提升 100×。
洞察 3: ternary > binary 不是反直觉, 是数学
ternary 多 51% 字节 (5.9 vs 3.9 GB), 换 5% 精度 (95 vs 90%), 单位精度字节成本反而低。对端到端部署: 笔记本选 ternary, 入门手机选 1-bit。
洞察 4: intelligence density 是新指标 (不是 bpw)
能力/GB 比 bpw 更能反映"塞进设备的能力"。1-bit Bonsai 0.53/GB, 是 FP16 10×, 是 Q4_K 的 4.5×。这是 Bonsai 引入的新一代评估指标。
洞察 5: DSpark + 1-bit = 端到端手机部署方案
87 tok/s (1-bit) + DSpark 2× ≈ 174 tok/s effective。DSpark + 1-bit 是 让 27B 模型能流畅对话的组合方案, iPhone 17 Pro 内存预算 (6GB) 刚好能装下。
