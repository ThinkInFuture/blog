0. Profiling 能回答什么问题

排查的起点很朴素：同一套 GLM-5.1 服务换了推理镜像后变慢——新镜像（10-09 构建，下文简称 1009）比老镜像（08-15 构建，下文简称 0815）的 TTFT（首 token 时延，用户发出请求到收到第一个字）慢了 15% 至 20%，到底慢在哪个算子上？端侧指标（TTFT/吞吐）只能说明“慢了”，profiling 才能回答“慢在谁身上、慢多少、什么 shape 下慢”。这次它交出的答案：

  • 阶段判定：decode 相所有 kernel 两版本无差距 → 排除 decode；
  • 算子定位：prefill 相 DispatchFFNCombine（MoE 通信融合算子）的大 chunk 调用变慢——shape [221,6144] P50 3436.9 → 3710.6us（+8%），且 1009 侧出现 p99 11088us 的长尾（单次最大 14.5ms）；
  • shape 锁定：慢的调用集中在 220~222 × 6144 的 prefill chunk（decode 形状 1~3 token 无回退）；
  • 归因延伸：顺着算子名去对比两版本 CANN 自定义算子包的 kernel 二进制（staticKey 全 DIFF），把结论钉死在“算子包实现变更”上。
为什么这些答案重要？ 端侧只能看到“TTFT 慢了 15%”，但没法知道是哪个算子、什么形状、什么阶段慢。Profiling 就像给 NPU 装了一个“行车记录仪”，能把每一次 kernel 执行的时间、形状、设备都录下来，据此精确锁定瓶颈。

没有 profiling，这个故事到“TTFT 慢 15-20%”就断了。

1. 怎么采：vllm serve 里的 --profiler-config + 短窗口姿势

1 挂参数 2 短窗口采集 3 其他要点

1.1 开关：它是 serve 的独立 CLI 参数

vllm-ascend 采集 NPU profiling 不用改代码，启动时挂上 --profiler-config（注意：独立参数，不是 additional_config 里的字段——放错位置 pydantic 会报 unexpected keyword）：

--profiler-config '{"profiler": "torch", "torch_profiler_dir": "/home/ywx1279670/profile", "torch_profiler_with_stack": false}'
  • profiler: "torch"：走 torch_npu profiler 路线（另有 mstx 等），导出 Ascend 侧解析结果；
  • torch_profiler_dir：数据落盘目录，确保所在盘有几十 GB 空闲；
  • torch_profiler_with_stack: false：不采调用栈。带栈的体积和噪声都大，定位 kernel 级问题不需要它。

1.2 短窗口姿势：这次最重要的一条经验

第一次全量采集直接干出 257GB，几乎导不动也析不动。后来固化成“压测中段 + 15 秒短窗口”的姿势，三个窗口 du -sh 实测 13GB / 14GB / 18GB（-93%），ASCEND 输出解析约 1.5 分钟：

图 1 · 短窗口采集姿势：257GB 教训 → 13~18GB（du -sh 实测：13 / 14 / 18GB）
为什么一定要中段采？ 压测刚开始时流量还在爬坡，请求没打满，采集到的数据不代表真实负载。等流量稳定后再采，才能反映真实压力下的表现。短窗口则让数据量小到可以快速分析，同时更容易对齐两个版本的采集条件。

1.3 其他实操要点

  • 只采一个 rank 就够入门：DP/EP 下每 rank 是一份完整 shard 的执行记录，定位单算子慢，先看 rank0（dp0_pp0_tp0），需要看通信对齐再扩到多 rank。
  • prefill / decode 分窗口采：这次就是分两次采的——decode 窗口 1010_cc8_mlapo、prefill 窗口 1010_cc8_prefill2（目录名＝采集日期_压测档_用途），天然把阶段分开，省得在一份数据里按 step 猜阶段。
  • 对照组条件对齐：基线（0815 镜像）与劣化（1009 镜像）用同一套压测参数（输入 3.5K + 输出 1.5K token、32 个请求、并发 8、不限发送速率）、同样窗口长度、同 rank，否则对比没有意义。

3.3 分析流程

图 2 · kernel_details.csv 分析五步：排行 → 分布 → shape → 对比 → 归因
为什么不能只看均值？ 均值会把“偶尔很慢”和“一直有点慢”混在一起。比如这次，全窗口池化后 1009 的 p50 反而更低，因为窗口里混了大量 ~300us 的 decode 小调用，把 prefill 大 chunk 的变慢稀释了。所以必须看 p99（长尾）并且按 shape 拆开。

3.4 pandas 模板（这次分析脚本的骨架，列名按真实文件写）

import pandas as pd, glob

# ---- 取文件：递归找 ASCEND_PROFILER_OUTPUT 下的 kernel_details.csv ----
f = glob.glob("/home/ywx1279670/profile/1010_cc8_prefill2/**/kernel_details.csv",
              recursive=True)[0]
df = pd.read_csv(f)          # 本例 209MB / 659657 行，读入约 1~2 分钟

dur, name, shp = "Duration(us)", "Name", "Input Shapes"

# ---- ① 全局排行：谁总耗时最大（等价于看 op_statistic.csv，但可算分位数）----
top = (df.groupby(name)[dur]
         .agg(cnt="count", total="sum", mean="mean",
              p50=lambda s: s.quantile(.5), p99=lambda s: s.quantile(.99))
         .sort_values("total", ascending=False).head(20))
print(top)

# ---- ② 锁定目标算子，看分布 ----
k = df[df[name].str.contains("DispatchFFNCombine", na=False)]
print(len(k), k[dur].mean(), k[dur].quantile(.5), k[dur].quantile(.99))

# ---- ③ 按 Input Shapes 分组（★关键：不按 shape 拆开看不到真差距）----
k = k.assign(shapes=k[shp].astype(str))
g = (k.groupby("shapes")[dur]
       .agg(cnt="count", mean="mean",
            p50=lambda s: s.quantile(.5), p99=lambda s: s.quantile(.99))
       .sort_values("cnt", ascending=False))
print(g.head(6))

# ---- ④ 两版本对齐对比：同一套聚合分别跑 0815 / 1009 目录后按 shapes 拼表 ----
# cmp = g0815.join(g1009, lsuffix="_0815", rsuffix="_1009")
# 只看“大 chunk”那几行（shapes 里首维 220~222），p50/p99 逐行对比

服务器上当时的分析脚本（/tmp/analyze_tri2.py 三边对比、/tmp/deep_analyse.py shape/重叠深挖）就是这个骨架加上多目录循环和输出整理。下面的实战复盘全部是按这个模板跑出来的真实数字。

排行本身就有信息量：1009 的集合通信便宜了很多（reduce_scatter 1489→172ms、allgather 1070→467ms，这是 1009 通信优化的收益），FFNCombine 总耗时反而还低了（4772→4574ms，调用次数还多 17%）。单看总量排名，根本发现不了回退——这正是第二步要按分布、第三步要按 shape 拆的原因。

4.2 第二步：锁 DispatchFFNCombine 看分布（全窗口池化）

### DispatchFFNCombine 对比（全窗口池化）
0815 {'cnt': 10218, 'mean': 467.0, 'p50': 304.8, 'p99': 3971.4, 'sum_s': 4.77}
1009 {'cnt': 12007, 'mean': 381.0, 'p50': 276.3, 'p99': 4116.7, 'sum_s': 4.57}

池化口径下 1009 的 p50 / mean 反而更低——因为窗口里混着两类调用：~300us 的 decode 形状小调用（1~3 token）和 3~4ms 的 prefill 大 chunk 调用，两个窗口里两类调用的比例不一样（1009 窗口小调用 11622 次 / 0815 窗口 9672 次），直接池化会被稀释甚至比反。必须按 Input Shapes 拆开。

这里最容易掉坑： 如果只看到池化后的数字（p50 更低），可能会错误地认为 1009 更快。但真相是：池化把两种完全不同的调用（decode 小调用 vs prefill 大 chunk）混在一起，而两个窗口里它们的比例不同，导致统计结果被“稀释”甚至“比反”。所以一定要按 Input Shapes 分组。

5. 坑与经验清单（都是这次交过学费的）

  • 数据量失控：全量采集 257GB——务必短窗口（12~15s）、关 with_stack、先查盘空间。
  • 窗口没对齐就开比：两份 profile 必须同压测参数、同窗口长度、同 rank；本例没有 profiler_info.json，就核对目录名里的时间戳。
  • 只看均值/总量会漏案，池化还会稀释差距：这次 FFNCombine 总耗时 4772→4574ms 反而更低、池化 p50 304.8→276.3 也是更低——直到按 Input Shapes 拆开才看到大 chunk +8%、p99 11088 的长尾。窗口里混着 decode 小调用和 prefill 大 chunk 时，比例不同就会把差距洗掉甚至比反，分布必须带 p50/p99、分组必须到 shape。
  • op_statistic.csv 看不到长尾：它是预聚合的，定位分布问题必须回到 kernel_details.csv 明细。
  • 阶段不分离会误判：prefill/decode 混在一份数据里，慢算子可能只是 decode 拖尾；分窗口采集（这次的做法）最省心，退而求其次用 shape/step_trace 分。
  • 归因要落到物：耗时对比只能说明“哪个算子慢”，要回答“为什么慢”得继续往下挖——对比 kernel 二进制（staticKey / md5）、翻算子包版本变更，或提单给算子团队带上两份 kernel_details.csv。
  • 解析工具别恋战：ASCEND_PROFILER_OUTPUT 自动产物优先；msprof --parse=on 失败就换路，别卡死一条道。
