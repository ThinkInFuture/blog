DeepEP 昇腾版解读：MoE 专家并行通信的实现与 CANN、vllm-ascend 衔接

lueelu/DeepEP 是面向 Ascend 950 的专家并行（EP）通信库：高吞吐 Prefill、低时延 Decode 共用一组 dispatch/combine 接口，另有把通信和专家计算融成一次前向的 MegaMoE。本文按源码讲清它的实现分层、与 DeepSeek 上游的关系、踩在 CANN 的哪几块地基上，以及 vllm-ascend 那边正在发生的衔接。

先给定位：MoE 模型做专家并行时，每个 rank 只持有一部分专家，前向要把 token 送去看得见对应专家的卡、算完再送回来——这两个动作就是 dispatch（分发）与 combine（归并），是 EP 通信里最吃带宽和时延的环节。这个仓库把这两个动作做成昇腾上的独立通信库，供推理与训练框架直接调用。

一、它是什么：一个库、三个能力

对外的能力面很收敛：一条 V2 接口 deep_ep.ElasticBuffer.dispatch() / combine() 同时覆盖高吞吐 Prefill 与低时延 Decode；一个实验入口 deep_ep_experimental.megamoe 把通信和专家计算融成一次前向；再加一组部署配置。README 的能力清单是三行：

  • 高吞吐 Prefill：基于 URMA 的 dispatch/combine，集成 notify 与 Server 级 token 去重，覆盖 EP32/64/128/256。
  • 低时延 Decode：同一 V2 接口的小批量路径，覆盖 EP64/128。
  • MegaMoE（实验性）：W4A8 量化推理（Prefill EP32/64/128，Decode EP64/128）与 BF16 推理、训练（Ascend950，训练走 PyTorch autograd）。

接口的形状从 README 示例就能看全：模型侧提供 x [T,H]、topk_idx [T,K]、topk_weights [T,K]（BF16 / INT64 / FP32），hidden 约束 0 < H ≤ 7168（BF16 按 16 对齐、FP8 按 128 对齐），topk 取 1~16。前向三步——dispatch、专家计算、combine——反向也复用同一组调用：

recv_x, recv_weights, handle = buffer.dispatch(x, topk_idx, topk_weights, num_experts, do_expand=True)
expert_out = local_experts_forward(recv_x, recv_weights)      # 专家计算由模型负责
out, _, event = buffer.combine(expert_out, handle)
event.current_stream_wait()                                   # 事件建立流依赖，CPU 返回 ≠ 设备完成

一个容易误读的参数：num_max_tokens_per_rank 是每 rank 的容量上限，不是本次实际 token 数；它同时是 HT / LL 的分档开关——≤ 256 走低时延，更大走高吞吐，容量上限 257 正是 vllm-ascend 集成里 DEEPEP_MIN_HIGH_THROUGHPUT_CAPACITY 的取值来源。

先看全景。仓库自带的架构图自上而下六层——推理与训练框架、DeepEP 接口契约、执行准备与启动、MegaMoE 实验入口、共享运行支撑，再往下是 Ascend C 算子层、SHMEM 与 CANN/硬件——整条依赖链一图收尽，后文按这六层展开：

三、实现分层：从 Python 接口到 Ascend C 算子

图 1 的每一层都能在仓库里找到对应目录。调用链在 docs/architecture.md 里只有一行：deep_ep.ElasticBuffer → deep_ep/buffers/elastic.py → deep_ep._C（csrc/bindings/module.cpp）→ csrc/ops → csrc/kernels 中的对应 kernel，最后落到「Python Runtime → C++ Session → SHMEM / CANN」。Host 层是 C++17，Device 子工程用 Bisheng 编译成 libdeepep_kernels.so——这正是图 1 里「Ascend C 算子层」的产物。

四、一次 MoE 前向：dispatch 与 combine 怎么走

路径分两种身份：首次进入的 fresh dispatch 要先跑 Notify——交换路由元数据、算出每个 rank 的接收计数和转发归并布局，然后才搬 payload；后续迭代手里已有 handle，cached dispatch 直接复用既有路由，跳过建表。combine 则始终按 handle 汇总专家输出。

三个设计细节值得注意：其一，展开布局保留每个有效专家槽位（包括重复路由），hidden、FP8 scale、路由权重按各自格式搬运；其二，专家计算保持 dispatch 给出的行顺序，combine 才能对回去；其三，权重乘法只做一次——推理在源 rank 归并时乘，训练在 GMM2 前乘，通信路径不自动对 hidden 乘 gate。HT 的 Session 把固定前半区留给 Notify/dispatch、后半区留给 combine，路由元数据和返回 Tensor 另有框架存储。

MegaMoE 是把上一节的两步通信再往前推一步：dispatch、GMM1、SwiGLU、GMM2、combine 五个动作融进一次前向调用，量化推理入口 fp8_fp4_mega_moe()，BF16 推理与训练共用 bf16_mega_moe()（训练经 PyTorch autograd 出输入、路由权重、专家权重三路梯度）。两条路共用 SymmBuffer、Host 扩展和 SHMEM 运行时；多机靠所有 rank 设置同一个 DEEPEP_SHMEM_ENDPOINT。另一个实验入口 EpGmmFused 则把 AllToAllV 与 GMM 双向拼接（AllToAllV→GMM、GMM→AllToAllV），走 UDMA 运行时。

六、三种拓扑入口：同一个库，三种组网

机器互联形态决定了能走哪条 kernel：仓库把入口分成三个，共 dependencies.lock.json 固定版本的 CANN SHMEM；「域」指物理互联域，不对应 EP/TP/PP 进程组，direct 只是内部实现名（按 EP peer 直接组织通信）。

Server 级去重的口径也写明了：当前实现按连续 8 个 rank 划分逻辑 Server 做 token 去重，逻辑 Server 不必与物理主机一一对应。装机前用 scripts/check_machine.py 校验物理卡号与期望拓扑（如全 Clos 八卡），输出 JSON 报告。默认分核为 32 AIV：V2 fresh dispatch 默认 32 核，cached dispatch 与 combine 沿用 handle 里的核数（含显式 64 核的 handle）。

七、踩在 CANN 的哪几块地基上

把图 1 底下三层拆开看，依赖链非常明确：

  • CANN SHMEM（通信基础）：对称工作区、远端访存、同步原语都从它来；版本由 dependencies.lock.json 锁定，wheel 自带构建所用的 SHMEM 运行库——装好后只需加载匹配的 CANN 环境，不必手动设 SHMEM_ROOT（它只决定构建时用哪个 SDK）。
  • URMA（高吞吐路径）：Prefill 的 dispatch/combine 基于统一远端内存访问；UDMA 则是 EpGmmFused 融合算子与 Global Clos 拓扑的运行时。
  • Ascend C / Bisheng（算子与编译）：设备算子用 Ascend C 写，Bisheng 编译成 libdeepep_kernels.so；CANN 9.2.0 配套 Q3 HDK 是 README 写明的性能前提。
  • CATLASS / CatCCOS（MegaMoE 计算）：融合算子里的两次专家 GMM 与量化由计算模板库承担，MegaMoE 构建脚本会准备 CATLASS 与 SHMEM 依赖。

版本门槛要念一遍：Linux、Ascend950、CANN 9.2.0（配套 Q3 HDK）、Python ≥ 3.11、PyTorch 与 torch_npu、CMake ≥ 3.20；构建期 DEEPEP_NPU_ARCH=Ascend950；运行期 DEEPEP_SHMEM_ENDPOINT（EP 作业共享初始化）与 ASCEND_RT_VISIBLE_DEVICES（设备分配）。

八、vllm-ascend 的衔接：一个未合入的实验 PR

衔接现状一句话：vllm-ascend 从 2026-04 起挂着 feature 请求（#8550），2026-11-06 出现实质进展——PR #21178 为 eager TP1/DP8/EP8 增加实验性 DeepEP HT 通信，硬件验证后移植到 main 分支，但截至本文写作尚未合入（closed, not merged），且默认关闭、opt-in。选它的 wheel 是刻意声明过的：ascend_deepep==0.1.0.dev5，构建自 lueelu/DeepEP 的 89e1939 提交——不是上游 CUDA 包。

集成代码不长，213 行新增里做了四件事：

  • token 分发封装：TokenDispatcherWithDeepEP 把 dispatch/combine 接进 MoE 的 token 流；同 shape 的层共享一个通信 Buffer，避免每层重建。

这个 PR 同时是 DeepEP 侧约束的活标本：DEEPEP_MIN_HIGH_THROUGHPUT_CAPACITY = 257 把容量上限钉在 257 以强制走 HT——正是第五节那条 ≤ 256 分档线的下游应用；单测覆盖补齐对齐、路由失效、combine 全员参与。也就是说，vllm-ascend 的实验主要在框架侧适配（路由对齐、Buffer 共享、动态库隔离），通信本体全部压在 DeepEP 库内。

九、上手路径与几条边界

把仓库自述的路径压缩成四步：

git clone https://github.com/lueelu/DeepEP.git && cd DeepEP
export DEEPEP_NPU_ARCH=Ascend950
python -m pip install -r requirements-build.txt
python -m pip install -v --no-build-isolation --no-deps .          # 发行包 ascend-deepep，导入名 deep_ep

几条边界读完源码就该知道：

  • 性能数字别提前引用：仓库自带 performance 图里，Decode 一张明确标着「待补充——BS 32 / 96 / 256 实测时延」；docs/performance.md 用整节篇幅立规矩——kernel 耗时 ≠ 端到端时延、单 rank 结果不能标为全作业耗时、dispatch 与 combine 的独立测量不能相加当作 roundtrip。
  • 拓扑选择是一次性的：构造 Buffer 时选定后端，后续 dispatch/combine 直接调对应实现；Mesh+PCIe 目前只对已适配的四卡 Mesh 产品开放。
  • 事件语义要按文档来：Python 方法返回和向流添加等待都不等于 CPU 已观察到设备完成；事件只是给消费流建立数据依赖。
  • 销毁要同序：所有 rank 以一致顺序执行通信与 buffer.destroy()，训练时 handle 要保留到反向结束。
收个尾：这个仓库把「EP 通信」从推理框架里拆出来单独做厚——接口收成 dispatch/combine 一对，底下按拓扑分三条 kernel 路径，再往上叠一个把通信和专家计算融成一体的 MegaMoE。对 vllm-ascend 而言，它补的是 MoE 专家并行在昇腾上一直缺的那块通信地基；PR 21178 尚未合入，但 213 行集成代码已经把「框架侧要做什么」演示得很具体。
