读前须知：八个名词 30 秒（更多见文末术语速查）
  • EngineCore / NPUWorker / NPUModelRunner：vLLM 上游的执行三级——引擎核心进程→每卡执行进程→每卡运行器；插件里对应 worker/ 与 model_runner 两层目录；
  • BalanceScheduler（DPLB）：排班员——决定本轮算哪些请求（DP 侧的负载均衡器）；
  • DSA-CP：DeepSeek 稀疏注意力在多卡间的序列并行通信模式（attention 的输入按序列切片、算前聚算后散）；
  • MTP / dspark / dflash：模型架构里的投机解码草稿头（MTP）；dspark、dflash 是两种草稿实现的名字；
  • EPLB：MoE 专家并行的负载均衡——按专家热度重摆专家副本；
  • prefix cache / chunkPrefill：算过的前缀直接复用 KV 块；长 prefill 切成多块分轮算；
  • TTFT / TPOT：首字延迟 / 每字延迟——压测两端的两个核心读数；
  • C8 / MLAPO：两个内部开关代号——C8=SFA 稀疏的 KV 存储块模式（enable_sparse_sfa_c8，随模型是否走 SFA 派生），MLAPO=MLA 相关融合优化开关（enable_mlapo，默认开）。

1. 全景：56 步四阶段主时序

这张图回答一个问题：一条请求从压测端打进来，到首字返回、再到流式吐完，路上每一步发生了什么、发生在哪个角色手里。横向是十条泳道——从最左的压测客户端，穿过 tokenizer、引擎（EngineCore）、排班（BalanceScheduler）、KV 块管理，到 Worker、运行器、模型实现，最后落在 parallel_state（HCCL 通信）与 torch_npu（CANN 算子）两件底座上；纵向按时间推进，分四个阶段。

图 1 · 全链路主时序：启动加载 → prefill → decode → 后台横切，56 步（宽图，可左右滑动）

阶段 0 · 启动加载（步 1 至 8）：把"能算"准备好——torch_npu/HCCL 初始化、进程组拉起、权重载入（多线程/lazy·NZ·W8A8·细粒度切分）、16 卡通信组、预编译与绑核、专家初始摆放、显存 profiling 建 KV 块池，最后探活就绪。这一阶段的关键产物是 KV 池与块表——后面 prefill/decode 都在它上面分配。

阶段 1 · prefill（步 9 至 39）：TTFT 的主体。HTTP 请求进来→文本转 token→引擎排队→排班→前缀缓存查命中（命中即复用 KV 块）→未命中则全量 prefill，长文切块分轮（图里 3.5K 长文切 4 块）→分配 KV 块写块表→下发执行→每卡只算 220 行的前向（步 20 至 32：SP 聚散、DSA-CP 三段流水、SFA 只算 topk 相关块、MoE 一笔融合、logits 分片归并）→采样挑首 token→一路回传→步 39 首字到手，TTFT 到此为止。

阶段 2 · decode 循环（步 40 至 51）：每步先查 stop 条件，再为新 token 追加 KV 槽位；decode 批下发后，MTP 草稿连猜 3 字、验证器留正确前缀，一步产出 1 至 4 个 token；增量结果流式回传，EOS 或达上限时释放 KV 块收尾。

阶段 3 · 后台横切（步 52 至 56）：与前台并行的几条侧线——每 600 步统计专家热度、热专家加副本重摆并搬权重（EPLB）；PD 分离部署时 KV 跨实例搬运（本链路未启用即空转）；指标上报与周期探活。

2. 阶段 0 的隐藏一步：模型注册表（补充）

时序图阶段 0 的步骤 3 写着"载入权重"——但权重还没载之前，有一件图里没画的事已经发生：哪个模型用哪套实现，早在引擎装配时就登记定死了。翻 vllm-ascend 源码的 models/__init__.py，会看到 24 条"架构名→实现类"的登记——这正是"哪个模型、应该用哪个配置"的答案所在：

图 2 · 阶段 0 放大：认模型一步（步 2.5）在载入权重之前——入口点→24 条注册表→查表取实现类
# setup.py:519-526 —— 插件把自己挂进 vLLM 的两排钩子
entry_points={
    "vllm.platform_plugins": ["ascend = vllm_ascend:register"],
    "vllm.general_plugins": [
        "ascend_kv_connector = vllm_ascend:register_connector",
        "ascend_model_loader = vllm_ascend:register_model_loader",
        "ascend_service_profiling = vllm_ascend:register_service_profiling",
        "ascend_model = vllm_ascend:register_model",   # ← 认模型挂在这
    ],
}

# vllm_ascend/__init__.py:100-105 —— 入口点进来后的包装
def register_model():
    from .models import register_model
    register_model()

# vllm_ascend/models/__init__.py —— 24 条登记（节选）
ModelRegistry.register_model(
    "DeepseekV4ForCausalLM",
    "vllm_ascend.models.deepseek_v4.model:AscendDeepseekV4ForCausalLM")
ModelRegistry.register_model(
    "KimiLinearForCausalLM",
    "vllm_ascend.models.kimi_k3:AscendKimiLinearForCausalLM")
ModelRegistry.register_model(
    "GlmMoeDsaForCausalLM",
    "vllm_ascend.models.deepseek_mtp:AscendGlmMoeDsaForCausalLM")
ModelRegistry.register_model(
    "Qwen3DSparkModel",
    "vllm_ascend.models.qwen3_dspark:AscendQwen3DSparkForCausalLM")
ModelRegistry.register_model(
    "DeepSeekV4MTPModel", "vllm_ascend.models.deepseek_v4.mtp:DeepSeekV4MTP")
# 全表 24 条；KimiK3ForCausalLM 是 KimiLinear 的兼容别名，指同一实现

机制链条四步：①插件安装时 setup.py 把 ascend_model = vllm_ascend:register_model 登记进 vLLM 的 general_plugins 入口点；②vLLM 启动装配时扫入口点、调 vllm_ascend 的包装函数；③包装函数执行 models/__init__.py 里的 24 条 ModelRegistry.register_model，把插件自己的实现类按架构名覆盖注册进上游注册表；④时序图步骤 3 载入权重时，上游按权重 config.json 的 architectures 字段查这张表——查到 AscendDeepseekV4ForCausalLM，后续步骤 20 至 32 的算子路径由此定型。登记之后还有第二层选择：attention 后端由 platform.py 按 hf_text_config 的字段（如 index_topk）决定走哪套注意力实现。

排查提示：模型没走上预期优化路径时，先查这两层
  • 第一层查注册表：权重 config.json 的 architectures 名是否在 24 条里——不在表里，上游走默认实现，算子路径完全不同（DeepSeek V4.1 走的是 AscendDeepseekV4ForCausalLM 这条登记）；
  • 第二层查后端条件：platform.py 的选路按模型字段判定（如 index_topk 决定稀疏注意力），字段对不上就走通用后端；
  • 两层都过了，才回到时序图对应步骤看执行路径——排查顺序与图的顺序一致：先认模型，再看执行。

BalanceScheduler（DPLB）排班器——DP 侧负载均衡，决定本轮算哪些请求
