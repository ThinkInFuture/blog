源码取自 vllm-project 主线（2026-10-20）＋ 组内真实启动脚本 · 2026-10-20
30 秒版本
  1. vLLM 世界分两层：vllm 核心管"模型实现"，vllm-ascend 是平台插件管"昇腾侧的一切"。
  2. 启动时 vllm 读权重的 config.json 里的 architectures（模型身份证）去注册表查类；NPU 上 vllm-ascend 会先用 register_model() 把少数"需要昇腾特化"的架构覆盖注册，查表结果就落到插件自己的实现上。

第 1 章 · 先分清两层仓库：谁管模型，谁管芯片

装好 vllm-ascend 后，环境里其实有三个角色。

  • vllm 核心（pip 包 vllm）管所有模型的通用实现——vllm/model_executor/models/ 下一个模型一个文件（glm4.py、deepseek_v2.py……），以及一张"身份证 → 实现类"的注册表。
  • vllm-ascend 不抄一遍所有模型，它只做芯片侧的事：注意力后端、通信、量化、自定义算子，外加少数非改不可的模型。
  • torch_npu + CANN 在最底下，把 PyTorch 算子落到昇腾芯片上执行。
图 1 · 三层分工：模型代码默认放核心，插件只补芯片侧的缺口
一句话记住分工 模型实现是"菜谱"（跟芯片无关），vllm-ascend 是"灶台适配器"（把同样的菜谱在昇腾灶台上做出同样味道）。菜谱不进灶台仓库——除非这道菜必须为昇腾灶台改刀工。

2.2 关键代码一：核心注册表里的 GLM 条目

vllm/model_executor/models/registry.py（vLLM 核心 · 2026-10-20 主线）
"Glm4ForCausalLM":        ("glm4",                     "Glm4ForCausalLM"),        # GLM-4 稠密/MoE 前代
"Glm4MoeForCausalLM":     ("glm4_moe",                 "Glm4MoeForCausalLM"),
"Glm4MoeLiteForCausalLM": ("glm4_moe_lite",            "Glm4MoeLiteForCausalLM"),
"GlmMoeDsaForCausalLM":   ("vllm.models.deepseek_v32", "GlmMoeDsaForCausalLM"),   # GLM-5.2 / 5.3：长在 DeepSeek 家族代码里
"Glm5NextForCausalLM":    ("vllm.models.glm5next",     "Glm5NextForCausalLM"),    # GLM-5.3-Flash：按厂商分目录的新式模型

两个值得注意的点：

  • GlmMoeDsa 的实现直接复用 DeepSeek 代码——GLM 5 系的 MoE + MLA + DSA 结构和 DeepSeek V3 系同源，注册表入口指到 vllm.models.deepseek_v32；
  • Glm5Next 用了"按厂商分目录"的新模式——核心里它长这样：
vllm/models/glm5next/__init__.py（核心侧只有通用代码 + 两家友商内核）
from vllm.platforms import current_platform
if current_platform.is_xpu():
    raise NotImplementedError("GLM-5.3-Flash does not currently support XPU.")
from .common.model import Glm5NextForCausalLM, Glm5NextForConditionalGeneration
from .common.mtp import Glm5NextMTP
目录结构：vllm/models/glm5next/{common/, nvidia/, amd/, sparse_indexer.py}——没有昇腾的份

2.3 关键代码二：插件侧的覆盖注册

vllm-ascend 安装时以 entry point 形式把 NPUPlatform 注册给 vllm；启动时平台插件会执行下面这段，同名架构后注册者生效（源码注释原话："overwrites the upstream architecture mapping"）：

vllm_ascend/models/__init__.py（NPU 平台启动时执行 · 摘录 GLM 相关条目）
ModelRegistry.register_model("GlmMoeDsaForCausalLM",
    "vllm_ascend.models.deepseek_mtp:AscendGlmMoeDsaForCausalLM")        # 覆盖核心实现
ModelRegistry.register_model("Glm5NextForCausalLM",
    "vllm_ascend.models.glm5next.model:Glm5NextForCausalLM")             # 昇腾版整套实现
ModelRegistry.register_model("Glm5NextForConditionalGeneration",
    "vllm_ascend.models.glm5next.model:Glm5NextForConditionalGeneration")
ModelRegistry.register_model("Glm5NextMTPModel",
    "vllm_ascend.models.glm5next.mtp:Glm5NextMTP")
ModelRegistry.register_model("Glm5DSparkForCausalLM",
    "vllm_ascend.models.glm5_dspark:Glm5DSparkForCausalLM")              # GLM5 投机解码草稿模型
这就是"启动分支"的全部含义 同一个架构名，在 GPU 上解析到核心实现，在 NPU 上解析到插件的 Ascend 版——分支不是 if-else 写在模型里，而是"注册表覆盖"发生在启动期。模型代码自己完全感知不到跑在哪种芯片上。

第 3 章 · 三个模型各走哪条分支

3.1 GLM-5.2 / GLM-5.3：GlmMoeDsa 一族——核心实现 ＋ NPU 小补丁

两代检查点组内部署形态：

  • 5.2 = GLM-5.2-W8A8C8-mxfp8（4 节点 32 卡 PD 分离）
  • 5.3 = GLM-5.3-W4A4C8-MXFP4（单机 8 卡，就是 A5 上那套）

它们是 MoE + MLA + DSA（稀疏注意力）同族，共享注册名 GlmMoeDsaForCausalLM，NPU 上被覆盖为 AscendGlmMoeDsaForCausalLM——打开一看，它几乎什么都没改：

vllm_ascend/models/deepseek_mtp.py（NPU 覆盖类 · 完整摘录主体）
class AscendGlmMoeDsaForCausalLM(GlmMoeDsaForCausalLM):     # 直接继承核心实现
    def load_weights(self, weights):
        mapper = WeightsMapper(orig_to_new_prefix={"rot.": None})  # 只处理 rot 前缀的权重映射
        return AutoWeightsLoader(self).load_weights(weights, mapper=mapper)

运行期的昇腾特色都在层和后端里，不在模型文件里：--quantization ascend（W4A4C8 / MXFP4 量化走 NPU 方案）、additional_config 里 enable_dsa_cp: true（DSA 的 CP 并行，就是之前 PR 18671 解读的那套）、MoE 通信走 MC2 融合算子。投机解码的 MTP 提议者也是 NPU 子类 AscendDeepSeekMTP，源码注释顺手给出了家族证据：

vllm_ascend/models/deepseek_mtp.py（注释原文）
# GLM-5.3 and friends ship no MTP head, leaving shared_head.head at
# its allocation-time contents. Record that so the proposer shares the target head.
→ GLM-5.3 这一代检查点不带 MTP 头，提议者直接借用主模型的 lm_head

5.2 与 5.3 共用同一架构名的依据：核心注册表里 5.x 的 MoE + DSA 只有这一个注册名；上面这条 "and friends" 注释；组内 5.2 / 5.3 部署走同一套 DSA / MTP / MC2 套件。严格确认以权重目录 config.json 的 architectures 字段为准（查法见第 5 章）。

3.2 GLM-5.3-Flash：Glm5Next——核心没有昇腾份，整套实现搬进插件

Flash 是另一条路：混合架构（一部分层 KDA 线性注意力 ＋ 一部分层全注意力）＋ 多模态 ＋ MTP。vLLM 核心为它设计了"按厂商分目录"的模式（common 通用骨架 ＋ nvidia / amd 各一份内核），昇腾的对应物没有进核心，而是整套放在插件里——vllm_ascend/models/glm5next/，一共 11 个文件：

文件干什么昇腾特色
model.py（44KB）模型主体（Glm5NextForCausalLM）被 register_model 覆盖注册的入口
kda.py（24KB）KDA 线性注意力层（继承 vLLM 的 GDN 基类）调 ops/kda.py 的 chunk_kda——就是上次精度问题的 chunk_kda_fwd CANN 算子；因果卷积走 AscendC causal_conv1d
attention.py（13KB）全注意力层NPU 稀疏注意力（DSA）路径
sparse_attn_indexer_kpool.pyDSA 稀疏索引器对照核心里 618 字节的接口 stub——核心只定义契约，各家给实现
kv_cache.py / cache_config.py / cache_views.pyKDA 状态 ＋ KV cache 管理KDA 的"笔记本"也要进 vLLM 的显存管理体系
mtp.py / multimodal.py / processor.pyMTP 层 / 多模态 / 预处理MTP 受 KDA 约束（见下方代码）
ops/（causal_conv1d、kda）昇腾算子入口Python 壳 → CANN 自定义算子

看 kda.py 开头几行，文件名和约束写得明明白白：

vllm_ascend/models/glm5next/kda.py（docstring 原文）
"""GLM-5.3-Flash KDA layer with separate convolutions and a bounded safe gate."""
class Glm5NextLinearAttention(GatedDeltaNetAttention):   # 继承 vLLM 的 GDN 基类
    ...
    from vllm_ascend.models.glm5next.ops.kda import KDA_MAX_RECURRENT_TOKENS, chunk_kda, recurrent_kda
硬约束（NPU 实现的边界，配错直接启动失败，这是好事）
    if config.linear_head_dim != 128 or dtype != torch.bfloat16:
        raise ValueError("GLM AscendC KDA requires BF16 activations and head_dim=128.")
    if num_spec + 1 > KDA_MAX_RECURRENT_TOKENS:
        raise ValueError("GLM AscendC KDA supports at most seven speculative tokens.")
还有一条细节注释：GLM-5.3-Flash 用有界 sigmoid 门控，不是默认的无界 softplus

第 4 章 · 回答标题问题：为什么 vllm_ascend\models 里"没有 glm"

4.1 先纠偏：其实有，只是不叫通常以为的那个名字

主线（2026-10-20）的 vllm_ascend/models/ 完整清单里有 glm5next/（11 个文件）和 glm5_dspark.py——GLM-5.3-Flash 的整套昇腾实现就在里面。

本地那份 vllm-ascend-main 代码如果翻不到，两种可能：

  • 下载得早（glm5next 是后来才合入的）；
  • 或者按 glm4.py / glm.py 这种"单文件名"习惯去找，漏了目录名。

验证方法：git log --oneline -- vllm_ascend/models/glm5next。全目录实拍：

类型条目
目录（6 个） glm5next/、deepseek_v4/、deepseek_v41/、minimax_m3/、common/、layer/
文件（12 个） glm5_dspark.py、deepseek_mtp.py、kimi_k3.py、kimi_k3_dspark.py、kimi_k3_mtp.py、llama_eagle3.py、llama_eagle3_vwn.py、gemma4_mm.py、qwen3_5_vl.py、qwen3_dspark.py、qwen3_dflash2.py、__init__.py（注册入口）

4.2 更重要的答案：什么模型才"有资格"进这个目录

这个目录的准入标准不是"是不是名模型"，而是"核心通用实现是不是搞不定"。三种情况：

  1. ① NPU 需要一整套自己的内核——GLM-5.3-Flash 的 KDA 层在 GPU 上靠 Triton / FLA 内核，昇腾上必须换 AscendC 算子（chunk_kda），连同因果卷积、DSA 索引器、cache 管理全得换 → 整套实现进插件（glm5next、deepseek_v4、kimi_k3 都属此类）；
  2. ② NPU 有专属预处理——qwen3_5_vl 的图像 resize / patchify 在 NPU 侧做融合 → 只把预处理部分搬进来；
  3. ③ 核心能跑但要小补丁——权重映射差异、个别算子行为差异 → 注册一个轻量子类覆盖，避免反向给核心提补丁的等待期（GlmMoeDsa 的 rot 前缀、MTP 的 head 处理）。
图 4 · 准入决策树：三道门，全过不了才"什么都不用做"——glm4 系列就停在最后一格

4.3 反过来：glm4 / glm4_moe 为什么不用进

GLM-4 系是标准结构（GQA 注意力 ＋ 标准 MoE ＋ RMSNorm / RoPE）。核心实现里这些全是 vLLM 的通用层——通用层在 NPU 上由 torch_npu 自动把算子派发到昇腾，注意力再由 vllm-ascend 的 NPU 后端接管，模型文件一行都不用抄。

这就是"菜谱不进灶台仓库"：适配的成本花在通用层一次性做掉，所有标准模型白拿收益。而 5.3-Flash 的 KDA 是新刀工，通用层里根本没有对应物，只能整套自己来。

第 5 章 · 自己动手查：三条命令

1) 看权重自报的架构名（启动分支的源头）
python -c "import json; print(json.load(open('/path/to/model/config.json'))['architectures'])"

2) 让注册表回答"这个架构在当前环境解析到哪个类"（含插件覆盖后的最终结果）
python -c "from vllm.model_executor.models.registry import ModelRegistry as R; \
print(R.resolve_model(['Glm5NextForCausalLM']))"

3) 看插件覆盖了哪些架构（GLM 相关的直接 grep）
grep -n "Glm" vllm_ascend/models/__init__.py

第 2 条命令在 NPU 环境和 x86 环境各跑一次，输出不同——这就是"启动分支"最直接的亲眼验证。启动日志里 platform 初始化段也会打出所选平台与注意力后端。

全文压缩成四句
  1. vllm 核心管模型实现与注册表，vllm-ascend 是平台插件管昇腾侧，两层靠"注册表覆盖"接线；
  2. 启动分支 = config.json 的 architectures 报名 → 插件 register_model() 覆盖注册 → 注册表给出最终实现类；
  3. GLM-5.2 / 5.3 走 GlmMoeDsaForCausalLM（核心 DeepSeek 家族实现 ＋ NPU 小补丁，DSA-CP / MC2 / MTP 都在层和后端），GLM-5.3-Flash 走 Glm5NextForCausalLM（核心只有 common / nvidia / amd，昇腾整套在 vllm_ascend/models/glm5next/，KDA 调 chunk_kda_fwd）；
  4. "models 里没有 glm"是误会——有 glm5next/ 和 glm5_dspark.py，其他 GLM 不进来是因为标准实现够用，不是没适配。

源码来源：vllm-project/vllm 与 vllm-project/vllm-ascend 主线（registry.py、vllm_ascend/models/__init__.py、glm5next/kda.py、deepseek_mtp.py、glm5_dspark.py，2026-10-20 拉取）；部署事实来自组内脚本实读。GLM-5.2/5.3 共用注册名为多证据推断，最终以权重 config.json 为准。
