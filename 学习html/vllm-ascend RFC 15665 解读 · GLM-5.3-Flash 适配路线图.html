上游 issue #15665 是 GLM-5.3-Flash 在 vLLM-Ascend 上的官方适配总跟踪单（RFC umbrella）——混合注意力栈、KeyPool 稀疏索引、混合缓存、MTP、并行、量化，所有工作项和验收口径都在这一个 issue 里滚动维护。

01三个组件分别是什么，为什么需要

GLM-5.3-Flash 的注意力栈不是一个新算子，而是三种机制拼起来的混合体。在讨论"适配难在哪"之前，先把三个组件单独拎出来——每个是什么、解决什么问题、代价是什么。理解了三者各自的动机，第二章把它们合在一起时，才能看清难点真正落在哪里。

1.1KDA 层：用固定状态替代线性增长的 KV

是什么：KDA 是一类线性注意力层。它不像标准 softmax 注意力那样把每个历史 token 的 K/V 全部存进 cache，而是用两组固定大小的状态承载历史——conv state 保存卷积窗口内的局部历史，recurrent state 按递推方式维护跨块的长期记忆。

为什么：标准注意力解码时每生成一个 token 都要读全部历史 KV，cache 随上下文线性增长。KDA 的状态大小固定，超长上下文下解码成本不会随长度膨胀。

代价：状态容量有限，无法像完整 KV 那样无损回看所有历史——所以必须与稀疏注意力配合，只在关键位置回看完整 KV。这就引出了下一个组件。

1.2NoPE Sparse MLA：把位置交给模型学，不做显式外推

是什么：MLA（Multi-head Latent Attention）是压缩 KV 的注意力结构；NoPE 指去掉 RoPE（旋转位置编码），rope_dim = 0。位置信息不再通过旋转显式注入 q/k，而是由模型在训练中学出相对位置表示。

为什么：RoPE 在训练长度之外需要插值 / 外推，长上下文时位置泛化是常见失效点。NoPE 把位置交给模型学习，配合稀疏选择（只回看相关位置），绕开显式位置外推。

注意：不能用"零填充 RoPE"假装等价——RFC 允许它做功能 smoke，但不允许当目标执行契约。

1.3KeyPool / KeyPoolIndexer：先选池，再展开 token

是什么：稀疏注意力的第一步是"选哪些历史位置"。旧方案 LightningIndexer 对每个 query 和每个历史 token 直接打分，选 top-k token。KeyPoolIndexer 改成两段式：先把历史 token 聚成"池"，对池打分选 top-k 池，再把选中的池展开成 token 索引，交给 SFA 做稀疏注意力。

为什么：token 级打分的成本随历史长度线性增长；池化后索引器只需对池数量打分（通常比 token 数少一个数量级），索引成本显著下降。

关键区别：KeyPool 的池表示参与模型语义，prefix 复用时必须完整恢复——它不是可丢弃的索引缓存。

02三种机制合在一起，为什么难适配

三个组件单独看都有清晰动机。但放进同一个模型层，问题从"三个独立组件"变成"三类状态在同一套调度里共存"——这才是适配难的真正来源。

三类状态各自有不同的生命周期、寻址方式和恢复语义，却必须同时喂给每一条下游链路：

  • MLA KV：无 RoPE 的主 KV，要按 block/slot 定位；
  • KeyPool / indexer 状态：参与模型语义，prefix 复用时必须完整恢复；
  • KDA 循环状态：随 token 递推演化，长度固定但需"快进"而非重算。
关键认知 · 不只是开算子

任何一条链路上状态对不齐，就是精度或功能事故。这也是 RFC 反复强调"合并 ≠ 验证完成"的根源——合并只说明代码进了主干，不说明这三类状态在五条链路上都被逐格验证过。

已合并的 #15127 提供了 Ascend 950 原生 FP8 的初始基线（KDA、稠密 NoPE MLA、基础 MTP、ACLGraph），但不包含训练时的 KeyPool 稀疏注意力路径——真正完整的路径靠后续一串 PR 补齐。

03三个设计支柱

RFC 的方案是：把 GLM-5.3-Flash 接入 vLLM-Ascend 现有的 SFA 基础设施，同时保留模型自定义的 KeyPool / KeyPoolIndexer 语义。落到三个支柱——每个支柱都明确切开"共享框架接口"与"模型私有实现"：

① Indexer 框架解耦 · #15669

KeyPoolIndexer 和 LightningIndexer 状态布局、打分语义都不同，不能互相映射实现。共享的只有生命周期、metadata、cache 所有权/更新、图执行、top-k 输出这些框架接口；KeyPool 的构建/打分/选择/token 映射留在模型侧。

② 混合缓存 · #15913

统一管理 MLA KV、KeyPool/indexer 状态、compressor 状态（如需）、KDA 循环状态四类状态，为 prefix caching、block/slot 映射、状态生命周期、容量核算、scheduler 准入打地基。后续 #17569（私有组路由，prefix caching 关闭）、#17545（small-slot 容量）继续补。

③ NoPE 原生 SFA · #16252 / #16756

rope_dim=0 在共享 SFA 后端原生支持；#16756 用原生 scatter 优化主 KV 写入。RFC 明确：可以用合成零填充 RoPE 做功能验证，但不允许把它当成目标执行契约。Flash3/MLAPO/PROLOG_V3 是后续按硬件与量化契约启用的优化。

05验证纪律（RFC 划的红线）

RFC 用了大量篇幅划红线——这些本质上都是"什么不能算证据"，对我们写实验结论同样适用：

模型专属证据

结构不同的 GLM 家族模型（如 GLM-5.2）的验证结果，不能算作 GLM-5.3-Flash 的正确性证据；共享框架的信心 ≠ 模型级结论。

CI 配置 ≠ nightly 通过

合并了 W8A8 测试配置 #18154/#18589，只说明"有这个配置"，注册的调度、真实执行的硬件 job、校准过的精度/性能基线是另外三回事。

容量 ≠ 正确性

缓存容量收益（如 LI INT8/FP8）不能替代精度与吞吐对等验证；容量优势不构成正确性证明。

优化要有 A/B

#19755 消除了 HBM 命中的外部探针，但 RFC 明说"无实测 E2E 加速、不声称 TTFT 改善"——没有硬件 A/B 的优化不能当性能证据。

reverted 不算落地

#17659 合并后被 #18307 revert，不算已落地的修复；#16584/#16290/#17012 关闭未合并，只是历史参考。图模式问题要对着目标 revision 复现。

Store 跨版本隔离

#19714 的恢复依赖 scheduler/worker 协议版本与 key→data 映射；升级若改变映射，必须隔离或重建旧 Store，禁止新旧条目混用。局部证据不能拼成组合证据。

一页结论

小结

① 5.3-Flash 在 vLLM-Ascend 的核心路径已通（KeyPool + NoPE SFA + KDA + 基础 MTP + C8）；② PCP、细粒度 prefix 复用、MTP 组合、torch.compile、LI 量化、硬件 nightly 是已知未完区，实验现象若落在这几格，先查对应 open PR；③ RFC 的验证纪律（模型专属证据、A/B、口径记录）可以直接当实验规范的上游依据。

06关键源码：框架接口与模型私有实现的分界

正文讲"三个支柱把共享框架接口与模型私有实现切开"，以下四段代码就是这条分界线的实物，全部取自 vllm-ascend 与上游 vLLM 的本地主线快照（行号为实测快照行号）。注释是逐行补写的原意说明。

① indexer 缓存层：让"非注意力"的缓存进入 KV 规划器

vllm_ascend/attention/indexer.py · L14-62（#15669 解耦后的框架侧最小实现）
class AscendSFAIndexerBackend(AttentionBackend):
    # 把 SFA indexer 的缓存登记为一个独立的 Attention 层：
    # KV-cache 规划器因此可以给它分配独立物理张量，
    # 同时与主 MLA 缓存组共享 block 编号。
    # 注意：这一层没有真正的注意力计算，
    # forward 仍然走真实 *.attn 层的 metadata。
    accept_output_buffer: bool = True

    @staticmethod
    def get_impl_cls():
        # 没有计算实现 —— 该层只承载缓存，返回 None 是刻意的
        return None

    @staticmethod
    def get_kv_cache_shape(num_blocks, block_size, num_kv_heads, head_size, cache_type=""):
        # 与主 KV 同构的四维形状：
        # [block 数, 每 block token 数, 头数, 头维]
        return (num_blocks, block_size, num_kv_heads, head_size)

    @staticmethod
    def get_supported_kernel_block_sizes():
        # vLLM 内部强制 block=128，与此处声明一致（见本文姊妹篇的实测注）
        return [128]

同一文件里的 AscendSFAIndexerMetadataBuilder（L65-93）是一个"cache-only" builder：build() 直接返回 None，不做任何 metadata 构建——docstring 明确说明不能复用 MLA 的 metadata builder，因为它假设 layer_names[0] 指向真实注意力对象，而 indexer 缓存层指向的是 DeepseekV32IndexerCache。这就是"框架接口共享、语义私有"的一个典型切面。

② SFA 主层：indexer 接线与 topk 门控

vllm_ascend/attention/sfa_v1.py · 约 L449-486（节选）
self.indexer = kwargs["indexer"]                    # 模型侧传入的 indexer：Lightning 或 KeyPool
self.skip_topk = kwargs.get("skip_topk", False)     # 跳过打分：直接消费缓存里的 topk 索引
self.topk_indices_buffer = kwargs.get("topk_indices_buffer")

# 是否走"索引缓存"路径：显式 skip_topk，或模型 config 声明共享 indexer 层
self.use_index_cache = self.skip_topk or index_cache_enabled
self.has_indexer = self.indexer is not None

if not self.has_indexer and not self.skip_topk:
    # 既没有 indexer、又不允许跳过打分 —— 直接报错，绝不静默降级
    raise ValueError("Indexer is required for DSA unless skip_topk is enabled. ...")
if not self.has_indexer and self.topk_indices_buffer is None:
    # 用缓存索引的前提是 buffer 存在
    raise ValueError("topk_indices_buffer is required when indexer is None and skip_topk is enabled. ...")

这段校验是 RFC 里"两种 indexer 不可互相映射实现"的工程落点：SFA 层只认 indexer 契约（谁打分、索引 buffer 从哪来），不关心打分是 token 级一段式还是池级两段式。同文件 L1137/L1213 处 Lightning 路径的旋转调用带 rope_dim=self.qk_rope_head_dim——NoPE 模型传入 rope_dim=0 时该调用退化为无操作，原生 NoPE 路径（#16252）就是绕开这种零填充。

③ KDA 前向：固定循环状态怎么进入分块递推

vllm_ascend/ops/triton/kda/kda.py · L1182-1210（入口节选）
def chunk_kda(
    q, k, v,                 # 查询 / 键 / 值
    g, beta,                 # g: 门控衰减系数（决定 recurrent state 的遗忘）；beta: 更新幅度
    scale=None,              # 默认 1/sqrt(d)，与标准点积注意力同口径
    initial_state=None,      # 跨块的循环状态（固定 d×d）——正文里 KDA 的"不写 KV 的长期记忆"
    output_final_state=False,
    use_qk_l2norm_in_kernel=False,
    cu_seqlens=None,         # 变长序列边界（packing 后的每序列起止）
    prebuilt_meta=None,
    **kwargs,
):
    if scale is None:
        scale = k.shape[-1] ** -0.5
    if use_qk_l2norm_in_kernel:
        # 归一化放进 kernel，避免额外一次全局 memory pass
        q = l2norm_fwd(q.contiguous(), use_tiled_kernel=True)
        k = l2norm_fwd(k.contiguous(), use_tiled_kernel=True)
    o, final_state = chunk_kda_fwd(
        q=q, k=k, v=v.contiguous(), g=g.contiguous(), beta=beta.contiguous(),
        scale=scale, initial_state=initial_state.contiguous(),
        output_final_state=output_final_state, cu_seqlens=cu_seqlens,
        prebuilt_meta=prebuilt_meta,
    )
    return o, final_state    # final_state 即下一块递推的起点状态

注意 initial_state / final_state 这一对参数：它们就是正文图 1 里的 recurrent state。prefix 复用时这类状态需要"快进"而非重算——这也是 RFC 把"循环状态随 prefix 快进"列为 prefix caching 校验格的原因。

④ 上游框架基座：一段式 indexer 的 CustomOp 抽层

vllm/model_executor/layers/sparse_attn_indexer.py · L729-760（节选）
class SparseAttnIndexer(CustomOp):
    # 把"打分选 top-k"抽成独立 CustomOp：mqa_logits / paged_mqa_logits /
    # top_k_per_row 这些重 kernel 按硬件后端各自实现。
    # 这正是 #15669 解耦的前提——框架管生命周期与 top-k 输出接口，
    # 模型（GLM-5.3-Flash 的 KeyPool）替换打分语义而不重写 SFA。
    def __init__(self, k_cache, quant_block_size, scale_fmt, topk_tokens,
                 head_dim, max_model_len, max_total_seq_len,
                 topk_indices_buffer, skip_k_cache_insert=False, use_fp4_cache=False):
        self.topk_tokens = topk_tokens                # 稀疏注意力回看的 token 数
        self.topk_indices_buffer = topk_indices_buffer # 一段式/两段式最终都输出这份索引集合
        # DCP/PCP 标量在模型构建期已确定，这里一次性解析，
        # 不再逐步 metadata 传递 —— 框架接口与并行拓扑的接触点
        self.dcp_world_size = parallel_config.decode_context_parallel_size
        self.use_pcp = parallel_config.prefill_context_parallel_size > 1
        self.cp_kv_cache_interleave_size = parallel_config.cp_kv_cache_interleave_size

forward_cuda 里最后把 topk_indices_buffer 交给 kernel——KeyPool 两段式的"选池再展开"最终也写回同一份 token 索引集合，这就是"模型语义私有、SFA 后端共享"的实现契约。
