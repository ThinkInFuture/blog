fla 库与 vllm-ascend：KDA 算子的源码血缘与三层分布

flash-linear-attention × vllm-ascend import / 版权头 / requirements 三证据实测 2026-10-20 发布 · 源码基线：本地 vllm-ascend 与 vllm 仓库 + fla main 分支

怎么读：一篇讲清一个关系——flash-linear-attention（fla）与 vllm-ascend 之间到底是什么依赖，KDA（Kimi Delta Attention）的算子在这条链上如何分布、为何同一算子出现两套名字。全部结论用三样东西钉死：源码 import、文件版权头、requirements 清单，基线为本地 vllm-ascend / vllm 仓库与 fla main 分支（2026-10-20 核实）。

1. 结论先行：不是 pip 依赖，是源码血缘

一句话关系：fla 库是 KDA 算子的上游基因库；vllm-ascend 不通过 pip 安装 fla（requirements 无 flash-linear-attention），而是经「vllm 主线 vendored → vllm-ascend 拷贝定制」两级源码血缘继承它，Triton kernel 全部内置在自己仓库里，另有 AscendC 原生算子这条 NPU 专属路径。

三证据（任何一处都可独立复核）：

证据一 import：vllm_ascend/ops/triton/kda/kda.py 只 import 自家子模块（chunk_delta_h / cumsum / fused_recurrent_kda / gate / l2norm / solve_tril）与 vllm.triton_utils，全程不出现 fla 包名；

证据二版权头：vllm-ascend 的通用版 ops/triton/fla/chunk_scaled_dot_kkt.py 头部明写 "This file contains code copied from the flash-linear-attention project"（MIT，Songlin Yang, Yu Zhang），而 KDA 定制版 kda.py 是华为版权的 vllm-ascend 项目文件；

证据三 requirements：vllm-ascend 的依赖清单里没有 flash-linear-attention——运行时零包依赖，全靠源码内置。

2. 源头：fla 库的 KDA 算子全集

生态位：MoonshotAI/Kimi-Linear 是论文仓库（仓库里只有文档、图表与 tech report），README 明说 KDA 内核并入 FLA 库 fla/ops/kda；官方高性能 CUDA kernel 另有 MoonshotAI/FlashKDA，fla 经 backends/flash_kda.py 接入（环境变量 FLA_FLASH_KDA=0 可回退 Triton 版）。

4. 同一算子，两套名字

命名分裂的由来：fla 库的惯例是「通用算子名 + _kda 后缀」（如 solve_tril 的 KDA 版叫 solve_tril_kda），vllm 生态则把 kda 插进中段。于是在 fla 风格代码里看到的 chunk_scaled_dot_kkt_kda，与 vllm / vllm-ascend 里的 chunk_kda_scaled_dot_kkt_fwd，是同一个算子的两种写法——干的都是 Chunk-KDA 第 2 步那件事。

decode 路径：短序列 / 逐步生成走 fused_recurrent_gated_delta_rule_fwd_kernel 单步更新隐状态并输出；另有 AscendC 原生算子路径（run_chunk_kda / run_recurrent_kda），以及 PR 15416 的门控投影双流重叠优化（fused_bfg_proj 一次 GEMM + 四事件调度），站内已有专门展开（见文末互链）。

6. 同源分家的另一分支：fla backends/triton_ascend

fla 自己也有 NPU 版：fla/ops/kda/backends/triton_ascend/ 下有 chunk_bwd / chunk_intra / chunk_intra_token_parallel / fused_recurrent / gate / wy_fast 六个文件，docstring 明写 "KDA chunk intra kernels for triton-ascend on Ascend NPU"，版权头是 fla 作者（MIT）。它与 vllm-ascend 的 ops/triton/kda/ 同一基因、各自维护：文件划分与命名都不同（fla 侧 chunk_kda_fwd_kernel_* 系，vllm-ascend 侧中段式），属于同一算法在两个仓库的平行实现。

为什么要分家：fla 是通用训练/推理库，走自己的 dispatch 机制（@dispatch('kda')）与 backends 目录；vllm-ascend 是推理引擎插件，kernel 要贴着 vLLM 的 triton_utils / 图捕获 / 双流调度走，还要与 AscendC 原生算子配合——两边诉求不同，各自演化比强行同步更实际。

小结：KDA 算子的世界地图 = 一个源头（fla，MIT）+ 一条主线继承（vllm vendored 1702 行）+ 一份 NPU 定制（vllm-ascend triton/kda 六文件 + AscendC 绑定）+ 一条平行分支（fla backends/triton_ascend）。看到任何 KDA kernel 名，先认命名风格（后缀式 = fla 系，中段式 = vllm 系），再对回六步链里的那一步，就能定位它在地图上的位置。
