核心分工逻辑：P 端解决「第一个字要多快」（TTFT），扩 P 台数直接压缩排队；D 端解决「后面每个字要多快」（TPOT）。三轮实验证明 TPOT 与 P 台数完全解耦（恒定 4.9~6.6ms）。P 端 1~3 台、每台 8 卡，形态 TP1 × PCP8 × DP1 + EP8，enforce-eager，prefix caching 开启；D 端 1 台 8 卡，形态 TP1 × DP8 + EP8，FULL_DECODE_ONLY 图模式 + dspark5 投机。

2. P 节点参数（Prefill 生产端）

2.1 并行形态与显存

参数当前值作用与配置理由
--tensor-parallel-size 1TP1层内张量不切分。P 端选 TP1 是实测定案：TP≥2 在该模型上有全局约束问题（历史 TP16/TP8 形态全部失败），全 TP1 形态是唯一跑通且最快的骨架。
--prefill-context-parallel-size 8PCP8P 端核心参数：prefill 序列切 8 份，8 卡各算 1/8 的 token（约 2560 tok/卡）。20K 输入的 prefill 时间被 8 卡分摊，TTFT 直接受益。KV 也按序列切，每卡只存自己那段的 KV——这就是 D 端要从 P 的 8 个 rank 各拉 1/8 KV 的原因。
--data-parallel-size 1DP1P 端无多副本。扩 prefill 吞吐靠「加机器」（2P/3P 多条 PCP8 流水线），已实测 C32 吞吐 1P→3P 提升 2.7 倍。
--enable-expert-parallelEP8MoE 专家切 8 卡，每卡持 1/8 专家。token 过 MoE 时经 All2All 送往持有对应专家的卡。模型大头（专家权重）因此每卡只有 1/8，稠密层（attention/共享参数）每卡完整一份——这正是 MoE 层里 PCP/EP 都进权重切分池的体现。
--gpu-memory-utilization 0.90.9每卡可用 HBM = 0.9×91.75GB ≈ 82.5GB，剩余给驱动/通信缓冲。0.92（D 端值）也可用，P 端取 0.9 是给 HCCL 通信缓冲与 KV 发送缓冲留空间。
--max-model-len 3276832K单请求最大上下文。压测 20K+385=24K 在限内；设 32K 是为兼容更长输入。
--block-size 3232KV 分块粒度（声明值）。实测注：vLLM 内部强制 block=128，此参数仅具声明意义，改动无效。

2.2 KV 传输参数（P 端作为生产者）

字段值作用与配置理由
kv_connectorMooncakeHybridConnector必须用 Hybrid 版。实测：旧版 MooncakeConnector 触发 Compressed caches must be packed 断言崩溃。它负责 prefill 完成后把 KV 推送给 D。
kv_rolekv_producerP 端角色为生产者：prefill 算完立即推 KV，不等 D 来拉（推拉结合由 connector 内部调度）。
kv_port20001KV 传输监听基端口。PCP8 的 8 个 rank 各占一个，实际监听 20001~20008（D 端按 rank 分别拉取）。端口冲突排查就是查这 8 个。
kv_buffer_devicenpuKV 传输缓冲走 NPU HBM（与 D 端 HCCL_BUFFSIZE=4096 配合）。
kv_connector_extra_config.prefill{tp:1, dp:1}向 D 声明「P 端 prefill 的拓扑」——D 端据此确定从哪些 rank 拉多少份 KV。必须与实际拓扑一致，不一致会导致静默重算（D 侧全量重算 prefill → 块荒死锁，联调期三天死锁的根因之一）。
kv_connector_extra_config.decode{dp:8, tp:1}声明 D 端拓扑（dp8×tp1），同理必须与 D 实际一致。
kv_load_failure_policyv4 默认KV 拉取失败时的策略。若允许 fallback 会回退本地重算（20K 重算约 20 秒 TTFT），压测中 TTFT 突刺即此信号。

2.3 调度与缓存参数

参数值作用与配置理由
--max-num-batched-tokens 81928192每调度步 token 预算：20K 输入 3 步铺完。调大（16384）可减步数，但单步耗时与通信量翻倍——待 A/B（本轮未做对照）。
--max-num-seqs 1616P 端并发容量：同时处理的请求数上限。C32/C64 压测时请求在此排队是高并发 TTFT 的组成项。提至 32/64 是明确的优化候选（低风险 A/B）。
--enable-prefix-caching开启命中率来源：相同前缀的 KV 复用（mix50 数据集实测 49.3%）。P 端必须开——命中率只在 P 端产生；D 端开反而无意义（见 D 端对应参数）。
--cp-kv-cache-interleave-size 11PCP 各 rank 的 KV 交织粒度。影响 KV 块组织与 D 端拉取的碎片数。官方默认 1，无调优参考数据，未动。
--dp-sync-interval 11DP 同步频率。实测对集合形状错位型死锁无救援作用，但保留无害；默认 16 改 1 属保险配置。
--enforce-eager强制 eagerP 端禁用图模式（对齐官方 CI 配方定案，无实测对照）。prefill 算子大、launch 占比低，图模式预期收益 5~15%——是待验证的优化候选（去 eager 做 A/B）。

2.4 量化与投机参数（P 端）

参数值作用与配置理由
--quantization deepseek_v4_fp8fp8官方原生权重零离线转换。引擎实际执行：MoE=W4A8-MXFP4 动态、稠密层=W8A8-MXFP8。唯一可行路线：modelslim w4a8 离线转换实测失败（weightScale 尺寸不符）。

3. D 节点参数（Decode 消费端）

3.1 并行形态与显存

参数值作用与配置理由
--data-parallel-size 8DP8D 端核心参数：8 个独立 decode 副本，各管各的请求（KV 按 DP 分，互不干扰）。TPOT 与并发解耦（C1~C128 恒定）的根源就是每 rank 独立流水。
--tensor-parallel-size 1TP1同 P 端理由（全局约束）。DP8×TP1 = 8 副本，每副本内 EP8 切专家——注意 MoE 层里 DP 也进专家切分池，dense 层才是真复制。
--max-num-seqs 6464D 端单 rank 并发 decode 容量 64。C128=512 条时每 rank 恰好 64 条——正好满载，已验证 C128 承载。
--max-num-batched-tokens 10241024decode 步的 token 预算（对齐官方 D 侧口径）。decode 每步每 seq 只产 1 token（+投机），预算天然小。
--gpu-memory-utilization 0.920.92D 端 KV cache 需求大（所有在途请求的完整 KV 都存 D），比 P 端多给 2%。
--no-enable-prefix-caching禁用D 端必须禁用：命中率只在 P 端产生（D 只做 decode 无 prefill，无前缀可复用）；且 kv_consumer 模式下开 prefix cache 与 KV 拉取路径冲突。

3.2 KV 传输参数（D 端作为消费者）

字段值作用与配置理由
kv_rolekv_consumer消费端：不接收完整输入，收到请求后按 kv_transfer_params 里 P 给的地址主动拉取 KV（实测 159MB/请求，8 rank 并行拉，1001 次全成功）。

3.3 编译与图模式（D 端 TPOT 的最大功臣）

参数值作用与配置理由
--compilation-config {"cudagraph_mode":"FULL_DECODE_ONLY"}FULL_DECODE_ONLYTPOT 218→16.4ms 的 13 倍功臣（10-27 实测）：decode 全程走 ACL Graph replay，消除逐算子 launch 开销。只对 decode 生效（prefill 不图）。
关联字段 cudagraph_decoder_replay 等默认decoder replay、capture sizes（实测 1~384 档位自动捕获）、trim_threshold=768——相邻 batch pad 到最近档位执行，相邻并发档 TPOT 持平即此效应（正常现象）。
--speculative-config {"num_speculative_tokens":5,"method":"dspark","enforce_eager":false}dspark5 + 图模式共存D 端真跑投机解码：draft 模型一次提 5 个候选，verify 步并行验证，实测采纳约 2.9 tok/步。官方口径 TPOT = 块口径 ÷ 采纳率 ≈ 16.5/2.9 ≈ 5.7ms。与图模式共存（MTP 才互斥）；enforce_eager:false 是投机路径上图的前提。
验证锚点—gsm8k 文本采纳率 2.95 vs random 文本 1.70（+27%）——所以 ais_bench（gsm8k）跑出 4.5~5.9ms 而自研 random 数据 7.2~7.6ms，两框架互证。

5. proxy 参数详解（请求入口与分流）

5.1 启动参数

参数当前值作用与配置理由
--host 0.0.0.0 --port 91000.0.0.0:9100proxy 监听端口。9100 是定案端口：9000 被宿主机 MindStudio 常驻服务占用（历史坑），9000 不可用。
--prefiller-hostsP 机 IP 列表（空格分隔）⚠ 127.0.0.1 陷阱：它指 proxy 所在机自己——proxy 不在 P 机上时这一路是空的。多 P 时建议全用实际 IP，不用 127.0.0.1。
--prefiller-ports8300 ×N与 hosts 一一对应。必须空格分隔（argparse nargs="+"，逗号串会报 invalid int——实测坑，重启脚本已生成空格形态）。
--decoder-hosts / --decoder-portsD 机卡间口 IP / 8301decode 腿目标，用卡间互联网段的 D 机 IP（由部署脚本自动登记）。多 P 时所有 P 机到该 IP 可达即可。
--max-retries 3 / --retry-delay 0.001默认后端请求失败的重试次数与退避基础延迟。
--max-waiting-retries 3 / --waiting-retry-interval默认后端未就绪时的等待重试（proxy 先于 P 起时自动等——但实测建议 proxy 在 P 就绪后再起：旧实例连接池失效会报 "Remote end closed"）。
--workers1（默认）uvicorn worker 进程数。实测单 worker 已承载 C64。
--enable-prefill-affinity不启用会话亲和：按 conversation key（model+system+首条 user message 的 SHA256）rendezvous hash 粘同一台 P。⚠ 对 mix50 数据集不生效——每条请求首条 message 不同（共享前缀藏在正文里），key 各不相同等于没粘。开启后 decode 仍均分。真要前缀粘性需按「前缀 N 字符 hash」改造，现有预热方案已够用故未做。
--log-levelINFODEBUG 可看每个请求的调度选择（排查分流用）。

5.2 调度机制（源码级实读，main 分支约 1440 行）

机制说明
SharedProxyScheduler（分数堆 least-load）每个 prefiller 维护 active_tokens 与 kv_cache 两个分数，请求派给总分最低者，完成时 release。实测铁证：2P/3P 各档 Δqueries 逐 token 级相等（164,07x / 2,625,1xx），精确均分。非朴素轮询——快机自然多接单。
taint（故障摘除）实例故障时加入 tainted 集合并重排堆，请求自动避开——多 P 挂一台不全瘫（分数堆重排到健康实例）。
两腿转发流程① prefill 腿：给请求加 do_remote_decode:true 的 kv_transfer_params → POST 选中 P → 等 P 返回（响应里带 KV 元数据）；② decode 腿：把 kv_transfer_params 塞回请求 POST 到 D → D 凭元数据拉 KV → 流式回包。
红线：kv_transfer_params 转发必须用官方 load_balance_proxy。此前简化版 proxy 不转发 kv_transfer_params（P 响应被丢弃）→ D 拿不到元数据 → 全量本地重算 20K → EP 集合错位 → 块荒死锁——11-06~11-07 三天事故的真凶。proxy 重启脚本特意把新旧三种 proxy 全清，防误用。
重启时机P/D 任一重启后 proxy 必须重启：旧实例到后端的连接池/会话状态失效，表现为请求被切连接（"Remote end closed connection without response"）。重启脚本一条命令完成清旧+bind 校验+重起。
