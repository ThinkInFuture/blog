▸概念爬坡 从普通 attention 爬到 SFA / indexer / DCP（五级）

爬坡第 1 级 · 普通 attention：每个 token 都要和全部历史算一遍 (普通 LLM 推理，你已懂，我们确认在同一页)

普通大模型推理里有两段：prefill 一次性把整段输入并行算完，decode 一个 token 一个 token 往下生成。生成时当前 query 要「回头看」之前所有 token 的键值对——这些键值对被存在 KV cache 里，attention 用它算当前 token 与每个历史 token 的相关性。序列越长，这一步要关联的历史就越多，成本大致是平方增长（O(n²)）。

爬坡图 0-1 · 普通 attention：query 对全部历史 key 打分概念爬坡 · 常识锚定（≤5 节点）
这张图回答什么问题：普通 attention 为什么是 O(n²)——每个 query 连向全部历史 key。
flowchart LR Q["当前 token 的 query"] --> A["attention 打分"] A --> K1["历史 key 1"] A --> K2["历史 key 2"] A --> K3["… 全部历史 key"] K1 & K2 & K3 --> V["加权求和 → 输出"]

解读：「全部」两个字就是后面所有故事的起点——长上下文时，这个「全部」让计算量暴涨，于是人们想：能不能只看一部分？

爬坡第 2 级 · 稀疏注意力：只看最相关的 k 个历史位置 (sparse attention)

因为「每个 query 都要关注全部历史」太贵，于是有了省事的办法：每个 query 只和自己最相关的 k 个历史位置算 attention。这种「只挑 k 个」的注意力，仓库里叫 SFA（稀疏注意力 backend，Sparse Flash Attention）。代价是：怎么挑出「最相关的 k 个」，本身需要一次计算。

爬坡图 0-2 · 稀疏注意力：query 只连 top-k 个历史位置概念爬坡 · 第 2 级（≤5 节点）
这张图回答什么问题：SFA 与普通 attention 的区别——参与打分的历史从「全部」变成「top-k」。
flowchart LR Q2["当前 token 的 query"] --> T["挑最相关的 k 个
（top-k 选择）"] T --> K1["第 1 相关位置"] T --> K2["第 2 相关位置"] T --> K3["… 第 k 相关位置"] K1 & K2 & K3 --> V2["只对这 k 个做加权求和"]

解读：从「和全部算」到「和 k 个算」，省的是算力；新增的成本是那个「挑选」。这一步的课题：挑选结果值得缓存吗？——下一级回答。

爬坡第 3 级 · indexer：负责挑 top-k，并把自己的决定缓存下来 (indexer / indexer cache)

因为「挑哪 k 个」的结论会被反复使用（同一位置可能被很多后续 token 查看），与其每次重算，不如让一个专门的模块负责挑选、并把决定存下来。这个模块就叫 indexer（索引器），它有自己的独立缓存（在仓库里按一种叫 LI-C8 的紧凑布局存放）。注意：indexer 缓存和主 KV 缓存是两套东西——一个存 key/value，一个存「该看哪几个位置」的索引。

这张图回答什么问题：indexer 凭什么独立存在——它有自己的一份缓存（LI-C8），跟主 KV 缓存分家。
flowchart LR Q3["query"] --> SFA["SFA 主注意力
用 KV cache 算 attention"] Q3 --> IDX["indexer（索引器）
挑 top-k 位置"] IDX --> IC["indexer cache（LI-C8）

解读：画面上已经出现两套缓存（主 KV 缓存 与 indexer 缓存）——「它们分别怎么存放」就是第 4 级的问题。

爬坡第 4 级 · 上下文太长切多卡：主缓存各管一段，indexer 缓存每卡一份 (DCP / PCP · rank-local vs replicated)

当上下文长到单卡放不下，vLLM 会把一个请求沿 token 序列方向切到多个 rank（卡）。这种「按序列切分」的并行，decode 阶段叫 DCP（decode 上下文并行），prefill 阶段叫 PCP（prefill 上下文并行）。切了之后两种缓存处理方式不一样：主 KV 缓存按 rank 各管各的一段（rank-local——每卡只存自己分到的那段历史）；indexer 缓存则选择每张卡都放一份完整副本（replicated——因为每卡都要快速查 top-k 结论）。

爬坡第 5 级 · 两种布局不一致 → 地址错配（本需求的痛点）

构建 indexer 元数据（比如「这次要写哪个缓存槽位」）时，如果用的是主缓存的 rank-local 地址——「槽位 7 在第 0 块缓存里」——而实际上 indexer 缓存是 replicated 的：每个 rank 各有自己的槽位 7。地址被用错语义，就会写到错的位置：不报错，而是悄悄把索引写乱，推理结果出错。这正是 PR #16325 要修的东西。

▸概览层 一句话：请求为什么会被「缓存地址错配」卡住

GLM-5.x 的稀疏注意力（SFA）在 Ascend 上多了一个 indexer（索引器）：每个 query 只关注 top-k 个历史位置，indexer 决定关注谁，它有自己独立的一份缓存。问题出在并行布局上——SFA 主缓存是 rank-local（每人只管自己分到的 token），而 indexer 缓存在 DCP rank 之间复制（每人一份完整副本）。构建 indexer 元数据时若沿用 SFA 的 rank-local 地址，就会把 top-k 索引写到错误的复制副本里，长输入精确检索直接错乱。

def build_sfa_dcp_replicated_block_table(
    dcp_block_table, seq_lens, block_table_output,
    replicated_col_idx, dcp_size, blocks_per_physical_block,
):
    """Expand a local SFA block table into replicated-indexer addresses."""
    local_col_idx = (
        replicated_col_idx // (dcp_size * blocks_per_physical_block)
        * blocks_per_physical_block
        + replicated_col_idx % blocks_per_physical_block
    )
    rank_in_replicated_view = (replicated_col_idx // blocks_per_physical_block) % dcp_size

    local_logical_blocks = torch.index_select(dcp_block_table, 1, local_col_idx)
    if blocks_per_physical_block == 1:
        # [关键] 核心换算：本地物理块 → replicated 块号
        replicated_blocks = local_logical_blocks * dcp_size + rank_in_replicated_view
    else:
        local_sub_blocks = local_logical_blocks % blocks_per_physical_block
        local_physical_blocks = local_logical_blocks // blocks_per_physical_block
        replicated_blocks = (
            local_physical_blocks * dcp_size + rank_in_replicated_view
        ) * blocks_per_physical_block + local_sub_blocks

    valid_req_mask = ((seq_lens[: dcp_block_table.shape[0]].to(device=dcp_block_table.device) > 0)
                      .to(replicated_blocks.dtype).view(-1, 1))
    block_table_output.copy_(replicated_blocks * valid_req_mask)
    return block_table_output
这段干嘛：地址变换纯函数（图 3 节点 3）。对应背景图 1-4 错误节点①的正解；块号按 DCP 世界大小拉伸，复制视图不再有 rank 私有语义。

def build_pcp_ordered_slot_mapping(
    global_slot_mapping: torch.Tensor,
    pcp_context: Any,
    slot_mapping_buffer: torch.Tensor,
) -> torch.Tensor:
    """Write slots in PCP gather order into a caller-owned output buffer."""
    gather_idx = pcp_context.padded_gather_idx
    write_mask = pcp_context.gathered_kv_write_mask
    if gather_idx is None or write_mask is None:
        raise RuntimeError("PCP+DCP prefill requires the PCP gathered-token layout.")
    num_tokens = gather_idx.numel()
    if slot_mapping_buffer.shape[0] < num_tokens:
        raise RuntimeError(
            f"PCP+DCP indexer slot buffer is too small: "
            f"capacity={slot_mapping_buffer.shape[0]}, required={num_tokens}.")
    slot_mapping = slot_mapping_buffer[:num_tokens]
    # [关键] 按 gather 顺序 index_select，再掩掉不写的 token
    torch.index_select(global_slot_mapping, 0, gather_idx, out=slot_mapping)
    slot_mapping.masked_fill_(~write_mask, -1)
    return slot_mapping
这段干嘛：共享 helper（图 3 节点 5）。SFA builder 与 indexer builder 共用它、各自保留存储——「单一事实来源」的落地。indexer 侧由 _build_pcp_ordered_slot_mapping（indexer.py L677）先组全局视图再调它。

    def _get_indexer_attn_metadata(self) -> Any | None:
        """只取 indexer 缓存层自己的元数据（由 indexer backend 构建）。"""
        if not self.runtime_has_indexer:
            return None
        own_prefix = self.indexer.k_cache.prefix

        kv_sharing_target = getattr(self, "kv_sharing_target_layer_name", None)
        if kv_sharing_target is not None:
