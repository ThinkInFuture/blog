"Legacy"这个词是源码自己写下的。往下翻还能看到更直接的证据：两套实现各有开关，同时打开会直接抛错；PCP 那套只在 Model Runner V2 引擎上可用，v1 引擎配了直接拒绝启动。一个文件、两代人、互不相容（图 1）——这就是本文要讲清楚的：它们分别怎么工作、交接班交接了什么、部署时该选哪条。

2. Legacy DSA-CP：一条私搭的 prefill 通道

DSA 模型的 KV cache 按 sequence 切成两段、分片存在 TP 组各卡上（省显存的代价）。prefill 时 query 要看全序列的 KV，于是需要一个"把分片重新组织起来算注意力"的机制——DSA-CP 就是这个机制，它是 vllm-ascend 为 DSA 一家私搭的，复杂度也全在"私搭"上：

  • 自己的 metadata 族：DSACPMetadata / AscendDSAReqMetadata / AscendDSACPLayerMetadata 一套四件，分片布局与 slot 换算全在 attention 后端内部完成，调度器对此一无所知；
  • 自己的通信编排：门口 all-gather 拼全量、o_proj 的 A2A head 互换、部分和归约——每一步都是文件内的私有逻辑；
  • 自己的邻居协商：想跟 SP MoE 配合，要靠 supports_sequence_parallel_input 那套三方握手（姊妹篇《SP MoE 与 DSA-CP》里的 #18671，修的正是这条通道上一笔"每层拼全量"的冗余）。

私搭通道的问题不在"跑不通"，在于每来一个新邻居都要重新协商一次：SP 来了协商一次，PD 分离来了再协商一次。这条全链见图 2。这笔学费交过之后，问题的通用性也暴露了——长 prefill 切多卡是所有长序列模型的公共需求，不该由 DSA 一家在 attention 后端里私搭。上游 vLLM 后来自己做了这件事，就是 PCP。

3. PCP：上游收编的通用能力

PCP 的原理一句话：在 Model Runner 的 batch 分区阶段，就把 prefill 的输入 token 切成 N 份分给 N 张卡，算完在引擎层合并。与 DSA-CP 的根本差别是位置：切分从 attention 后端内部上移到了引擎层，调度器、metadata、attention 全链路都知道"这个 batch 是切过的"——邻居们（SP、PD、投机解码）从此跟引擎层打交道，不用再跟 DSA-CP 一个个握手。

4. 三个类与一条继承链：交接班交接了什么

回到 dsa_cp.py。文件后半的 PCP 实现与 Legacy 的继承关系，就是这次交接班的交接书：

vllm_ascend/attention/context_parallel/dsa_cp.py · L2129-2133（PCP 版 Impl 类头）
class AscendDSAPCPImpl(dsa_v1.AscendDSAImpl):
    """Run batched global DSA cache updates before rank-local PCP attention."""

    supports_pcp: ClassVar[bool] = True

PCP 版 Impl 继承 dsa_v1.AscendDSAImpl——DSA 的稀疏注意力内核、indexer、compressor 一概不动。换班换的不是计算，是三段外围编排：

  • 输入侧：各 rank 拿到本地分片的 padded batch，attention 前先 all-gather 拼回全局，再按 hidden_restore_idx 恢复调度器原序（去掉 padding 空位）；
  • 缓存侧：SWA / compressor / indexer 三类缓存的写入统一用全局 slot_mapping——每个 rank 基于同一份全局视图写缓存，不再是 Legacy 的分片存储按需聚合；
  • 输出侧：_get_o_proj_input_shape 只报本地行数，o_proj 各算各的段，跨 rank 合并交回引擎层。
vllm_ascend/attention/context_parallel/dsa_cp.py · L2139-2152（PCP：全局聚合还原调度序）
def _gather_and_restore_hidden_states(self, hidden_states, metadata):
    """All-gather one padded rank slice and restore scheduler token order."""
    gathered_hidden_states = get_pcp_group().all_gather(
        hidden_states.contiguous(),
        dim=0,
    )
    return torch.index_select(
        gathered_hidden_states,
        0,
        metadata.hidden_restore_idx,     # ← 恢复调度器原序（去 padding）
    )
vllm_ascend/attention/context_parallel/dsa_cp.py · L2160-2180（PCP：复制的 SWA 缓存全局更新一次）
def _update_global_swa_cache(self, layer_name, global_hidden_states, swa_kv_cache, swa_metadata):
    """Update the replicated SWA cache from the canonical global batch."""
    req_metadata = dsa_v1._require_req_metadata(swa_metadata)
    assert req_metadata.slot_mapping is not None

    kv = self.kv_norm(self.wkv(global_hidden_states))
    kv = kv.view(-1, 1, self.nope_head_dim + self.rope_head_dim)
    torch.ops._C_ascend.inplace_partial_rotary_mul(kv.unsqueeze(1), ...)
    get_dsa_attn_kv_plan(self.vllm_config).dsa_kv_compress_scatter(
        swa_kv_cache,
        kv,
        req_metadata.slot_mapping,     # ← 全局 slot_mapping：每 rank 用同一份全局视图写缓存
    )
取舍PCP 用"缓存复制"换工程简洁：每个 PCP rank 持有全局 KV 视图的副本（显存开销高于 DSA-CP 的分片存储（数据面差异见图 4）），换来的是不再需要为每个邻居单点协商。另外 sparse MLA 场景下，PCP 暂只支持 eager 或 FULL_DECODE_ONLY 图模式。

5. 选路代码：两个开关为何互斥

后端入口的选路函数把两代关系写得最直白（builder 与 impl 两层各有一份同样的判断）：

vllm_ascend/attention/dsa_v1.py · L110-131（get_builder_cls：入口三分支）
from vllm_ascend.utils import enable_dsa_cp

use_dsa_cp = enable_dsa_cp()
use_pcp = enable_pcp()
if use_dsa_cp and use_pcp:
    raise ValueError("Legacy DSACP and PCP cannot be enabled at the same time.")
if use_dsa_cp:
    from vllm_ascend.attention.context_parallel.dsa_cp import AscendDSACPMetadataBuilder

    return AscendDSACPMetadataBuilder          # ← Legacy DSA-CP（additional_config 开关）
if use_pcp:
    from vllm_ascend.attention.context_parallel.dsa_cp import AscendDSAPCPMetadataBuilder

    return AscendDSAPCPMetadataBuilder         # ← PCP（--prefill-context-parallel-size 开关）
return AscendDSAMetadataBuilder

enable_pcp() 读上游通用并行配置，enable_dsa_cp() 读昇腾私有配置（并自动收敛到统一校验路径——模型没有 indexer 时强制回 false）。互斥的合理性正在于此：两个开关管的是同一个位置的两代人，运行时只能有一套在岗。源码里没有给 Legacy 标废弃日期，但"新增量全在 PCP、Legacy 只收不再发"的态势，从这条选路函数就能读出来。

6. 部署视角：两条路径的边界与代价

把散在各文件的校验集中成一张边界清单：

  • PCP 仅 v2 引擎：v1 配 PCP 直接 ValueError（platform.py 校验，报错原文"PCP is not supported by vLLM Ascend"）；
  • PCP 五不开：PP>1、encoder-decoder 模型、多模态输入、LoRA、投机解码（pcp_manager.py 逐项 NotImplementedError）——MTP 用户暂留 Legacy；
  • 与 Legacy DSA-CP 互斥：两开关同开直接抛错；
  • sparse MLA 图模式受限：仅 eager 或 FULL_DECODE_ONLY；
  • SP 共存：SP 开着时 max_num_batched_tokens 被自动改写成 tp_size × pcp_size 的整数倍（warning 日志，自动适配非报错）。

选型上的对应结论：新部署（GLM / DeepSeek 长序列 prefill 场景）优先评估 PCP，对照上面清单过边界；存量 v1 + DSA-CP 部署仍是当期能跑的正式路径，尤其依赖 MTP 的场景，等 PCP 把投机解码边界补齐再迁移不迟。

7. 从 2291 行到 218 行：两种开发姿势

最后看一眼体量：Legacy DSA-CP 的主场文件 2291 行，PCP 的昇腾侧接入层 218 行。差距不是代码功力，是姿势——前者是"缺什么自己在 attention 后端里搭什么"，通信编排、metadata、邻居协商全部私有；后者是"上游把通用能力做好，平台层写薄壳接入"，私有代码只剩昇腾特有的 graph 对齐与缓存细节。

这也是读懂 vllm-ascend 演进的一把钥匙：DSA-CP、SP 直通协商这类"平台私搭"的产物，会随着对应能力被上游收编而逐个进入维护态——代码还在、开关还在、存量部署还能跑，但新增量不再灌注。看一个特性是活是暮，先看它的新提交还多不多、以及上游有没有长出同名能力，比看任何文档都准。
