一张图看全 msProf 从应用层打点到 AI Core PMU 寄存器的采集链路。左侧层级、中间组件与硬件框图、 右侧采集项三列严格对齐；Host 与 Device 由一条虚线切开；L5 展开 950 的 AI Subsystem 内部结构， 并用彩色圆点标出每个采集项在硬件上的实际取数位置。

msProf 的采集不是单一动作。它沿「用户打点 → CANN 收敛参数 → 驱动开通道 → 硬件单元出数据」这条链路逐段完成，每一层都有各自的数据来源和采集开销： L1 依赖用户主动埋点，L2 是 Host 侧 CPU 开销，L3 是 Host/Device 之间的传输，L4~L6 才是真正的 NPU 硬件数据。 有了这张分层视图，profile 结果里一条异常耗时才能被定位到具体环节——是应用埋点、调度排队，还是计算单元本身。950 的关键变化集中在 L4~L6：STARS2.0 的调度轨迹、AIC/AIV 分离后的 PMU、以及 Cube 的 L0C 与 Vector 的 UB 之间的 CV 直通通道。

怎么读这张图

从下往上定位、从上往下归因，是 profile 分析的两条常用路径

从下往上定位。拿到一份 msProf 结果，先看 L6 的 L2 带宽和 L5 的 PMU 利用率：如果 Cube 利用率已经饱和，说明计算单元是瓶颈，往上走意义不大； 如果 Cube 利用率低但 L4 的 task 排队时间很长，问题就在调度层；如果 L1 应用层打点显示耗时高、而底层所有硬件利用率都低，问题很可能在 Host 侧的调度或同步上。

从上往下归因。反过来，当用户报告「某个算子慢」，先从 L1 找到该算子，看它在 L2 的 API 耗时、L4 的 task 轨迹、L5 的 PMU 指标是否一致。 一致说明问题就在这个算子本身；不一致则说明上层打点与底层执行之间存在错位，最常见的是异步下发导致的打点时间与实际执行时间不重合。

950 上最需要改变习惯的是 L5 和 L6。前代芯片 Cube 和 Vector 耦合较紧，很多分析习惯上会把二者作为一个整体看； 950 分离之后，AIC 与 AIV 的 PMU 数据是并行产生的，同一个 Subsystem 内 1 个 AIC 和 2 个 AIV 各自的利用率、流水停顿都可能不同，必须按 coreType 分开看， 否则会把一个已经饱和的 Cube 和一个大量空转的 Vector 平均成一个「看起来还不错」的中间值。

950 采集的三个关键变化

相对上一代，profile 数据的解读方式需要相应调整

syscnt 替代 cycle 计数

950 的 AICore 新增 syscnt 寄存器，task-based 采集得到的 aicore_time 基于系统时钟而非周期计数，因此不再受调频影响。

这意味着不同任务、不同算子之间的耗时可以直接横向比较，不必再像以前那样担心频率波动导致的数据失真。

CV 直通后 L2 数据「变少」

L0C 到 UB 的直通通道启用后，Cube 的输出可以直接搬进 Vector 的 UB，不再经过 L2 中转。L2 带宽计数器因此会下降。

这不等于访存效率变差。判断是否正常，要看 PipeTimeline 中 Fixpipe 是否在持续工作——只要 Fixpipe 忙，说明数据在走直通通道，L2 数据低是预期行为。

1 AIC : 2 AIV 的 PMU 并行

一个 AI Subsystem 内，AIC 与两个 AIV 同时产生 PMU 数据，采集时通过 coreType 字段区分。

在 timeline 上必须拆成独立泳道观察。把 AIV 的矢量利用率当作 Cube 的利用率，是 950 上最容易犯的误读。

怎么用这张图定位问题：同一层里，左侧的层级、中间的组件与右侧的采集项是一一对应的——先确定耗时落在哪一层，再取该层右侧列出的采集项， 就能拿到对应的硬件数据。层与层之间的连接行标出数据流向（上报、下发、调度、访存），Host / Device 虚线标出哪些数据要跨过 HDC 通道回到主机侧。 L5 是唯一横向展开的层（AI Subsystem 内部结构），它的采集项与上方 L4 的调度轨迹、下方 L6 的存储计数构成一条完整链路。
