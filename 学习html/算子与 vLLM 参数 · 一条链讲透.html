算子与 vLLM 参数：一条链讲透

启动命令里的每个参数，最终都落到 device 上一串具体的 kernel。这篇用 GLM-5.1 的真实启动参数 + 真实 op_statistic.csv，讲清"参数 → 框架执行路径 → 算子 → profiling"这条链，以及怎么反向从算子排行反推配置。

vLLM 源码 · 2026-10-16 发布 · 参数→算子链路实战笔记

一句话总结：启动命令里的每个参数，最终都会变成 NPU 上一串具体的 kernel。读懂 参数 → 框架路径 → 算子 → profiling 这条链，就能正向预测一个参数会动哪些算子，也能反向从算子排行反推它跑的是什么配置。

0. 三层视角：参数、路径、算子

同一次推理可以从三层看：配置层（启动敲进的参数）、框架层（vllm / vllm-ascend 据此组织的执行路径）、算子层（NPU 上真正跑的 kernel）。profiling（op_statistic.csv / kernel_details.csv）就是算子层的观测窗口。

图 1 · 三层视角：参数改的是框架路径，profiling 看到的是路径的最终投影
为什么要打通这条链
  • 正向：改一个参数前，能预测哪些 kernel 会变——验证开关是否生效、评估收益来源；
  • 反向：拿到任何一份 op_statistic.csv，能反推它是什么配置、什么模型跑出来的——排查线上问题、看别人环境的第一步。

1. 参数影响算子的四种方式

所有参数对算子的影响，归纳起来就四种，每种都能在这次的真实数据里找到例子。先记住这四个分类，后面所有排查都会用到它。

方式含义真实例子（GLM-5.1）
① 换实现同一份计算逻辑，换不同 kernel（甚至融合成一个大算子）enable_fused_mc2=1：MoE 的 dispatch+FFN+combine 融合成 DispatchFFNCombine 一个 kernel（占 40.5%）；关掉则变成 MoeDistributeDispatchV2 + 专家 MatMul + CombineV2 三个
② 换 shapekernel 名不变，但调用的 shape / 次数变了--enable-chunked-prefill + CP 切片：3.5K prompt 的 MoE 调用 shape 是 220~222×6144 的 chunk，不是整条 3.5K；num_speculative_tokens=3：decode 每 step 1~4 个 token（shape [1~4,6144]）
③ 增删算子开了新路径，出现原本没有的 kernelenable_dsa_cp（DSA 稀疏注意力）→ 出现 SparseFlashAttention（9.3%）+ Indexer 相关小 kernel（IndexCheck 等）；--quantization ascend → 出现 QuantBatchMatmulV3（10.9%）+ AscendQuantV2（2.6%）
④ 改执行方式kernel 清单不变，改的是怎么调度执行cudagraph_mode FULL_DECODE_ONLY：decode 走图模式，kernel 名一个不变，变的是 host 侧 launch 方式（间隔更密、CPU 开销小）；--async-scheduling、multi stream 同理
推论排查"改了参数为什么没效果"时先归类：如果是 ①③ 类参数，op_statistic.csv 里必须能看到 kernel 清单变化——看不到就是参数没生效（没被解析、名字不匹配、走了回退分支）；如果是 ② 类，要去看 kernel_details 的 Input Shapes；如果是 ④ 类，kernel 层面根本看不出差别，得看 host 侧（api_statistic）或端侧指标。

4. ② 换 shape 的实例：shape 里藏着配置信息

4.1 prefill 的 220~222 是怎么来的

压测输入 3.5K token，经 CP=16 切片（每卡约 219 token）+ chunked prefill 按块组 batch 后，落到每卡单次 MoE 调用就是 [220~222, 6144] 的 chunk。所以看到 FFNCombine 的 Input Shapes 首维在 220 附近，就能反推：输入约 3.5K、CP=16、chunked prefill 开着。反过来，decode 的 shape 首维 = 1 + draft 数：mtp num=3 时每 step 最多 4 个 token（1 个真实 + 3 个 draft 并行验证），窗口里看到的是 [1~3, 6144]。

4.2 用"调用次数对齐"认亲：谁跟着谁走

kernel 之间的次数关系能暴露它们的归属路径，这次窗口里有两对精准对齐：

对齐关系说明什么
ForeachAddList 12008 次 ≈ DispatchFFNCombine 12007 次每次 MoE 调用后跟一次残差/列表加法——ForeachAddList 是 MoE 路径的随从，FFNCombine 走融合路径，它就同步存在
0815 窗口：ScatterNdUpdate 10611 次 == SparseFlashAttention 10611 次每次注意力计算后一次 KV cache 散射写入——KV 写入跟着 attention 走，次数一致说明每层每 chunk 写一次

方法：把候选 kernel 的 Count 列放一起比，成对出现的就在同一条执行路径上。版本升级后某个 kernel 从 top10 消失（如 1009 窗口 ScatterNdUpdate 不在了），先查它是不是被融合/改名，再看调用次数去哪了——不要直接当成"优化掉了"。

6. 验证"参数真的生效"：三板斧

改完参数不确定有没有生效？按成本从低到高，依次用这三招验证：

手段看什么本例
① 服务日志回显启动日志 non-default args 段有没有新参数（最快，零成本）enable_prefill_mc2: True 回显确认配置进去了
② kernel 清单 diff开关前后各采 15s，diff op_statistic 的 OP Type 清单与占比（①③ 类参数必变；② 类看 shape；④ 类不变）fused_mc2 关/开 → DispatchFFNCombine 行消失/出现；enable_prefill_mc2 开后 TTFT 753-768 持平 → 生效但无收益
③ 端侧指标交叉TTFT / TPOT 方向与算子变化自洽FFNCombine 大 chunk +8% ↔ TTFT 差 15-20%（它占 40.5%，量级吻合）

注意 ② 的坑：有的开关生效后 kernel 名不变（改 shape/调度），diff 清单会一无所获——先判断参数属于第 1 节的哪一类，再决定看哪张表。

7. 常见疑问

  • Q：AivKernel 是什么？
    A：AI Vector Core 上一类 vector 小算子的聚合名（foreach、index、cast 等 elementwise 操作会归到这类名字），单个 15us 左右但次数多（7.8 万次），靠次数堆出 8.5%。分析时把它当"vector 杂项池"，要看明细得回 kernel_details 按 Name+shape 拆。
  • Q：MIX_AIC 是什么？
    A：Cube+Vector 混合执行的大算子（融合算子多为 MIX_AIC），通常单次耗时长，是 top10 里的重量级选手。
  • Q：为什么有些代码里的算子在 profiling 里找不到同名？
    A：图融合 pass / 静态图会把多个小算子合成一个（名字变成融合后的），或 aten 层算子最终下发的 aclnn kernel 名和 Python 层名字不同。对不上时用 shape + 调用次数去认，不要死磕名字。
  • Q：通信算子去哪看？
    A：op_statistic 里 AicpuKernel 结尾的（allgather/reduce_scatter）是通信；EP 的 all-to-all、卡间矩阵在 communication.json / communication_matrix.json 里，按需加载。
