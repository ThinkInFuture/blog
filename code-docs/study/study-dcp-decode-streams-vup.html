阶段一 · 背景：DCP decode 现在怎么跑，卡在哪

▼

1.1 这个需求在 vllm-ascend 里的定位

上游 vLLM 为 DeepSeek 系模型定义了 MLA 注意力接口（MLAAttentionImpl）和 DCP 的切分语义——把 KV cache 按 sequence 维分片、决定"谁算历史、谁算当前、怎么合并"。vllm-ascend 负责的是执行： vllm_ascend/attention/mla_v1.py 里的 AscendMLAImpl（mla_v1.py:795）是昇腾上的 MLA 注意力后端，真正干活的是昇腾 CANN 的 FIA 融合算子； attention/context_parallel/mla_cp.py 里的 AscendMlaDCPImpl（mla_cp.py:232）混入上游的 DCPImplMixin、继承 AscendMLAImpl——既遵守上游 DCP 的接口约定，又复用昇腾的 MLA 执行能力。这就是典型的 Ascend 适配层结构：上游管语义，昇腾管执行。

DCP decode 一步要把注意力拆成两段：HISTORY 段（历史 token 的 KV，本 rank 只有 1/dcp_size 分片，算完要把 partial 结果经 all-to-all 交换拼回完整）和 CURRENT 段（当前 chunk 的 KV 各 rank 都有副本，本地直接算）。两段各自输出 partial 注意力和 LSE，最后用 LSE 合并（数学上等价于对全序列做一次 softmax）。合并后的输出是 batch-major 布局，还要做一次 V-up 投影才能交给下一层。

1.2 现状与三个痛点

改造前这条链路能跑、数值也对，但藏着三处浪费：

  • 痛点① dtype 转换：history 段的 partial 输出和 LSE 在送进 all-to-all 融合算子前被显式 .float() 转成 FP32——这是两次全量张量拷贝 + 精度转换，而下游合并其实直接支持 BF16/FP16，这次转换纯属保守写法的浪费；
  • 痛点② 计算排在主流：current 段 FIA 排在主流上执行，主流同时还背负着后续的合并、本层收尾和下一层任务；而 all-to-all 的打包阶段（展平、组包）和通信占着另一条流——"计算"和"通信"没有各自站在最合适的那条流上；
  • 痛点③ V-up 多两次转置：合并后的 batch-major 输出做 V-up 要 transpose → bmm → transpose，两次显存搬运只为凑布局。

decode 阶段每秒要跑几十上百步、几十层，这三处每步都发生，累积起来就是可观的时延。

阶段二 · 方案：三处浪费，三个拆法

▼

2.1 设计思路总览

这个 PR 的方案可以概括成一句话：把 dtype 转换删掉、把计算和通信在两条流上的分工对调、把 V-up 的三次算子融成一次。三者互相独立，可以分别验证——这也体现在测试上：回归测试同时覆盖了"流顺序"和"BF16/FP16/FP32 三种 history 输出 dtype"两组场景。

第一刀：dtype 直通。all-to-all 融合算子 sfa_dcp_a2a_fused 与合并算子 fused_sfa_dcp_lse_combine 本身支持 BF16/FP16，中间那次 .float() 转换并不承担任何语义（合并的数学对 dtype 不敏感，精度由测试锁住），删掉后 history 的 partial 输出和 LSE 以原始 dtype 直接进通信，省掉两次全量拷贝。

第二刀：流职责对调（本 PR 的灵魂）。原编排是"通信在侧流、计算在主流"；新编排把 current 段 FIA 整个搬到侧流（attn_stream），主流腾出来做 history 的打包与 all-to-all。为什么这样对调更优？三个理由：① 依赖更干净——current 段的输入（current_q/current_k/attn_mask）与 history 段的输出没有数据依赖，唯一的约束是两次 FIA 共用 workspace、必须保持先后，用一个 record_event / wait_event 就能表达；② 主流归还给通信——集合通信在主流发起是 HCCL 的常规用法，打包+发出一气呵成，不再被计算插队；③ 重叠窗口对等——current FIA 的整个执行时长与主流"打包 + 通信"的时长重叠，decode 的当前 chunk 只有 1 个 token、计算很快，把它从主流队尾挪走后，主流干完通信只需等一个事件就能合并。

跨流三纪律（这是本方案最值得学的部分）：① 顺序靠事件——history_ready = main_stream.record_event() 在 history FIA 之后打点，侧流 wait_event(history_ready) 后才动 workspace；② 生命周期靠 record_stream——主流分配、侧流使用的输入张量要 record_stream(attn_stream)，防止分配器在侧流还在读时就回收；侧流产出、主流消费的结果反向 record_stream(main_stream)；③ 汇合靠 join——主流 wait_event(current_attn_done) 之后才允许 combine 读侧流结果。

第三刀：V-up 融合 + 回退守卫。torch_npu.npu_transpose_batchmatmul 允许用 perm_x1 / perm_y 声明两次置换，把"transpose → bmm → transpose"融成一次算子调用，省两次显存搬运。但该算子对 batch×K 维度有 65536 的上限（这里 batch 维是 num_heads、K 维是 kv_lora_rank），所以代码里留了守卫：范围内走融合算子，超限自动回退 torch.bmm 原路径——"融合 + 回退"是接入昇腾融合算子的标准姿势，值得记住。

与老流程怎么接：不改任何接口与配置（PR 明确 no user-facing change）；DCP 的切分语义仍归上游，本 PR 只重排昇腾侧的执行编排；两次 FIA 共享 workspace 的图捕获逻辑保持不变（注释同步更新了原因表述）。

还有一条值得学的反面决策：这个 PR 没有顺手把 prefill 路径也切到新编排——prefill 的 current 段是整个 chunk、计算量大，与通信重叠的收益模型完全不同，硬套会引入更复杂的事件链却换不到收益。把方案克制在 decode 路径内，是「一次只改一个执行编排」的典型取舍，也让回归测试的爆炸半径可控。

阶段三 · 实现：顺着调用链读代码

▼

3.1 执行入口与两段输入的拆分

整个故事的舞台是 AscendMlaDCPImpl（vllm_ascend/attention/context_parallel/mla_cp.py:232）的 decode 路径。它继承 AscendMLAImpl（复用昇腾 MLA 的投影与 V-up）、混入上游 DCPImplMixin（遵守上游 DCP 接口）。进入 decode 前元数据已经把 sequence 维切成两份：HISTORY 组带 block_table 与 cp_history_seq_len（本 rank 分片上的分页 KV），CURRENT 组只有当前 chunk 的 K/V 加一个 attn_mask（sparse_mode=3 的当前窗口掩码）。两次注意力调用用的是同一个方法 _run_dcp_mtp_split_attention_op（mla_cp.py:391），只换 attention_kind 枚举——这是理解本 PR 的钥匙：两段计算本身是对称的，不对称的是它们的编排位置。

先看一个容易被忽略的前置步骤（本 PR 只更新了它的注释，mla_cp.py:530 附近）：进入 FIA 之前要为算子准备 workspace（算子工作区）。图模式（ACL Graph）下算子输入输出地址必须固定，所以代码按 num_tokens 预分配一块 workspace、取所有候选里最大的那个，两次 FIA 共用同一块。这决定了后面事件顺序的语义：侧流上的 current FIA 必须等主流上的 history FIA 用完 workspace 才能动它——不是数据依赖，是工作区复用的顺序依赖。

3.2 代码怎么落：四处关键改动

第一处：history FIA 照旧在主流（mla_cp.py:578-590）。用 MLASplitAttentionKind.HISTORY 调 FIA，输入是分页的 history K/V 与 block_table，产出 partial 输出和 LSE。这一段没有改动，是后面所有编排的锚点。

第二处：current FIA 搬进侧流（mla_cp.py:592-621）。这是本 PR 的灵魂，三行一个节奏：history_ready = main_stream.record_event() 在 history FIA 之后打点；五个跨流输入张量（current 的 q_nope/q_pe/k_nope/k_pe 和 attn_mask）逐个 record_stream(attn_stream)，向分配器声明"这些张量还要在侧流上用"；进入 with torch.npu.stream(attn_stream) 后先 wait_event(history_ready)（保护 workspace 顺序），再跑 CURRENT FIA，最后 record_event(current_attn_done)。出了 with 块，结果两个张量反向 record_stream(main_stream)——侧流生产、主流消费，生命周期声明一个都不能少。

第三处：主流直接做 all-to-all，去掉 .float()（mla_cp.py:622-630）。sfa_dcp_a2a_fused 现在在主流上执行，直接吃 BF16/FP16 的 history 输出与 LSE（旧版的 .float() 两次全量拷贝被整体删除），defer_combine=True 把合并推迟到本地一步做。随后 main_stream.wait_event(current_attn_done)——join 点，主流在此等侧流的 current FIA 收工。

第四处：合并且不打包 current（mla_cp.py:632-640）+ V-up 融合（mla_v1.py:1000-1010）。fused_sfa_dcp_lse_combine（来自 ops/triton/sfa_cp.py）把 a2a 收齐的历史分片与侧流直接产出的 current 结果做 LSE 合并——旧版要把 current 也打包进合并输入，新版用 local_output/local_lse 参数直读，省一次打包。最后 _v_up_proj_batch_major 收尾：batch-major 输入不再转置，npu_transpose_batchmatmul 用 perm_x1=(1,0,2), perm_y=(1,0,2) 一次完成两个置换加批矩阵乘；num_heads × kv_lora_rank 在 [1, 65536) 内走融合算子，超限回退 torch.bmm（守卫常量在 mla_v1.py:73）。

测试怎么锁住行为：tests/ut/attention/test_mla_cp.py 扩到 27 个用例，新增流顺序断言（侧流结果必须晚于 history FIA）和 BF16/FP16/FP32 三种 history 输出的参数化；精度侧用 DeepSeek-V3.1-Terminus W4A8 TP8/DCP8 跑 100 条 GSM8K，evaluator 精度 95%——证明删掉的 .float() 确实不承担语义。

TRANSPOSE_BMM_MAX_SUPPORTED_DIM = 65536  # ⚡融合算子上限：超出自动回退 torch.bmm

    def _v_up_proj_batch_major(self, x: torch.Tensor) -> torch.Tensor:
        """Keep the DCP result batch-major and fuse both BMM permutations."""
        x = x.view(-1, self.num_heads, self.kv_lora_rank)  # ↳ batch-major 输入，不再先转置
        # The operator's batch dimension is num_heads, not the token count.
        if 1 <= self.num_heads * self.kv_lora_rank < TRANSPOSE_BMM_MAX_SUPPORTED_DIM:
            # ⚡两个置换 + 一次 bmm 融成单算子（→NPU torch_npu 融合算子通道）
            x = torch_npu.npu_transpose_batchmatmul(x, self.W_UV, perm_x1=(1, 0, 2), perm_y=(1, 0, 2))
        else:
            x = torch.bmm(x.transpose(0, 1), self.W_UV).transpose(0, 1)  # ↳ 回退路径：与旧实现等价
        return x.reshape(-1, self.num_heads * self.v_head_dim)

3.3 学完这个 PR，带走三个可复用的套路

  • dtype 直通审查：链条上每个显式 .float() / .to(dtype) 都要问一句"下游真的需要吗"——由合并算子的 dtype 支持面和精度测试回答，而不是靠保守转换；
  • 跨流三纪律：事件建顺序（含 workspace 这类非数据依赖）、record_stream 声明生命周期、join 点显式等待——三条缺一，错的是难复现的显存回收竞态或脏读；
  • 融合 + 回退：接入 torch_npu 融合算子时查清维度上限，代码里留守卫回退到等价的朴素路径，上限以内吃性能、超限不崩。
