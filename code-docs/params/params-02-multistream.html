多流类参数：绑核与双流重叠

参数组 2/8 · 多流 代码基线 a71b766ce（2026-09-23）
讲解范围：vllm_ascend/ascend_config.py 顶层三参数 enable_cpu_binding（L458，默认 true）、multistream_dsv4_dsa_overlap（L459，默认 true）、 multistream_overlap_shared_expert（L461，默认 false），及三个实现位置： worker/worker.py + cpu_binding.py（绑核）、 attention/dsa_v1.py（DSA prolog 双流）、ops/fused_moe/shared_experts.py（共享专家双流）。

① 这段代码是干嘛的

一句话：这三个参数管"并发度"——一个管 host 侧稳不稳，两个管 device 侧挤不挤。 推理一步的耗时 = host 准备（组 batch、填元数据、启动算子）+ device 执行。host 准备的节奏不稳， 芯片就会"饿"；device 侧如果所有算子排一条队，不同硬件单元也会互相干等。这三个参数各堵一个漏：

  • enable_cpu_binding（CPU 绑核）：把每个 worker 进程钉在它那块 NPU 对应的 CPU 核上， 防止操作系统把进程挪来挪去造成喂卡节奏抖动；
  • multistream_dsv4_dsa_overlap（DSA prolog 双流）：DeepSeek 系注意力的 prolog（前处理）里 投影/量化/归一化在 Cube、Vector 两类硬件单元间交替，单流排队时互相干等——拆两条流流水起来；
  • multistream_overlap_shared_expert（共享专家双流）：MoE 里每个 token 都要过的 共享专家，把它的输入准备/计算挪到独立流，与路由专家路径同时跑。

③ 概念爬坡：从"排队"走到"三个开关"

级 1 · NPU 的任务不是"立刻执行"，是"提交进队列"。你写 c = a + b 这样的 张量运算，程序并没当场算完——它只是把一条"做一次加法"的指令提交到了芯片的任务队列里， 真正的执行由芯片异步完成。这个队列在昇腾/英伟达的编程模型里叫 stream（流）： 同一流里的任务严格按提交顺序串行执行；不同流之间不保证顺序，可以并行。 默认情况下所有任务都提交到同一条"默认流"。

级 2 · 单流的问题：芯片单元之间的"空转隙"。昇腾芯片里干活的单元分两类： Cube（矩阵乘法专用单元，干大 GEMM）和 Vector（向量运算单元，干归一化/量化/逐元素）。 它们是两套独立硬件。但单流队列是串行的：前面的 Vector 算子（比如量化）没跑完， 后面的 Cube 算子（矩阵乘）只能干等——哪怕 Cube 单元此刻完全空闲。这种交替越频繁，空转隙越多。 注意力 prolog 恰好就是"Vector、Cube 交替"的重灾区。

级 3 · 双流 + 事件：把"无依赖"的活挪过去，依赖用事件声明。解法是把互不依赖的任务 提交到第二条流（辅助流）并行跑。但"无依赖"必须精确声明：如果辅助流上的任务 X 需要主流上 任务 Y 的产出，就要用 event（事件）——主流在 Y 完成处"记录事件"，辅助流"等待该事件"后才跑 X。 事件就是跨流的"哨兵"。等两条流的活都干完，再汇合（主流等辅助流）继续。

级 4 · 昇腾上的三个落点。有了"流+事件"这套工具，回看推理链路上哪里在浪费并发： host 侧，worker 进程被操作系统在 CPU 核间搬家，喂卡节奏时快时慢——把它钉到专属核（绑核）； device 侧，注意力 prolog 的 V/C 交替（图 3-2）用双流流水化解；MoE 的共享专家与路由专家 互不依赖却排一条队——也用双流并行。这就是三个参数的全部由来。

⑤ 关键节点逐个展开：三个参数

5.1 enable_cpu_binding —— 把 worker 进程"钉"在专属 CPU 核上

病：decode 每步都要 host 侧先干活（组 batch、算元数据、提交算子）。如果操作系统 看哪个核空闲就把 worker 进程搬过去，进程会遭遇缓存失效、跨 NUMA 访问、与其它进程争抢—— 喂卡节奏从稳定的 5ms 偶尔抖到 20ms，芯片跟着饿肚子。多卡服务器上问题更明显：几十个 worker 进程若无约束，可能挤到同几个核上。

治法：cpu_binding.py 在初始化时用 npu-smi 拓扑信息解析出 每块 NPU 亲和的 CPU 核列表（哪个核离哪块芯片近、属于哪个 NUMA 域），worker 按 local_rank 选出自己的核集合，写进进程的 CPU 亲和性掩码——从此 OS 只能把它调度在这些核上。 注意容错：绑核失败（权限/拓扑解析失败）只打 warning 不阻断启动。

5.2 multistream_dsv4_dsa_overlap —— 注意力 prolog 的三段流水

病：DeepSeek 系 MLA 注意力的 prolog（前处理）序列是典型的 V/C 交替： q 路量化（V）→ q 投影（C）→ kv 路量化（V）→ kv 矩阵乘（C）→ kv 归一化（V）……单流串行时 两套硬件单元轮流空转。

治法：_mla_prolog_multistream（dsa_v1.py:1919）把它拆成三段两流的流水： 主流与辅助流（dsv4_dsa_overlap_stream()，dsa_v1.py:179 的单例流）交替推进，用 事件接力保证依赖。最值得学的是源码注释里点出的硬件约束： 让 Vector 型的 kv_norm 排在 Cube 型的 kv_matmul 之后于辅助流执行，是为了避免两者争抢 Cube 单元—— 双流不是"随便并行"，要按硬件单元分派任务。

5.3 multistream_overlap_shared_expert —— 共享专家与路由路径并行

病：MoE 层里专家分两种：路由专家（每个 token 按门控分发给少数几个）和 共享专家（每个 token 都必须过，承担"公共知识"）。两者逻辑上互不依赖， 但默认排同一条流：共享专家的输入聚合（all-gather）与计算，把路由路径的启动往后顶。

治法：shared_experts.py 给共享专家单独一条流 （shared_experts_calculation_stream()）：prepare_input_async（L246）把 SP 模式下的输入 all-gather 挪到共享专家流，与路由侧的输入变换（如 Kimi-K3 的 latent 投影）重叠； 计算入口再按开关切换（L565 的 enabled=self.multistream_overlap）。 开关读取在 AscendSharedExperts.__init__（L92）。

⑥ 流工具：npu_stream_switch 与两个单例流

读完三处实现会发现它们用的是同一套流工具，这是 vllm-ascend 封装好的"双流姿势"： npu_stream_switch(stream, enabled=开关) 是一个上下文管理器——进入时把"当前流"切到目标流 （开关关闭时什么都不做，代码写一遍即可同时支持开/关两种模式），退出时切回； dsv4_dsa_overlap_stream()（dsa_v1.py:179）和 shared_experts_calculation_stream() 都是单例获取函数——首次调用创建流，之后复用同一实例，避免反复建流的开销。 三处实现的代码形状因此完全一致：record_event → with switch: wait_event → 干活 → record_event。

⑦ 边界与异常：互斥、死锁坑与降级

  • 静默互斥：enable_fused_mc2=1 时 multistream_overlap_shared_expert 被强制改回 false（ascend_config.py:705-706）—— 你配了也白配，日志无 error。排查"共享专家重叠为什么没生效"先查 mc2。
  • HCCL 死锁坑：shared_experts 注释原话——TP 的 all-gather 必须留在默认流；若挪到共享专家流而 routed 侧 EP 集合通信在默认流， 两个进程组进度不一致可能死锁 HCCL。双流与集合通信混排时要问一句"这个集合操作在哪个进程组、哪条流"。
  • 绑核失败降级：bind_cpus 抛异常只 warning、服务照常启动（worker.py:937-938）—— 排查性能抖动时确认日志里有没有这条 warning（绑核可能根本没生效）。
  • 默认值即态度：dsv4 双流默认开（成熟），共享专家双流默认关（较新+有互斥）—— 升级配置时别想当然。
