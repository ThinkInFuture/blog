① 全景：两条采集线，一套上游骨架

推理服务的性能采集要回答两类问题："哪个算子慢"（算子/内核级）和 "服务流程哪一段慢"（调度、批处理、KV 管理的函数级）。昇腾官方指南给出两条对应的采集线：

特性线一：Ascend PyTorch Profiler线二：MS Service Profiler
安装内置，命令行即开需从源码构建 msserviceprofiler（CANN Toolkit 预装）
采集粒度PyTorch 算子级服务框架函数级（也可含算子）
控制方式API 请求控制（/start_profile、/stop_profile）配置文件控制（enable 0→1）
数据格式ascend_pt 格式Chrome Tracing + CSV
适用场景模型算子性能分析服务框架工作流分析

两条线共用上游 vLLM 的骨架：ProfilerConfig（参数）、 Worker.profile()（入口）、WorkerProfiler（生命周期状态机）。 vllm-ascend 做两件事：把线一的执行器换成 torch_npu.profiler； 给线二生成昇腾专用的符号打点表。这就是本页的两条主线。

② 线一：Ascend PyTorch Profiler（算子级）

2.1 使用流程：五步拿数据

启动服务时带 --profiler-config（只设了它，/start_profile 端点才会注册，否则 404）； 稳定后 curl 开采集 → 跑业务请求 → curl 停采集 → 离线 analyse → 用 MindStudio Insight 看。 注意 2026-01-19 起上游废弃了 VLLM_TORCH_PROFILER_DIR 环境变量（vllm-ascend PR #5928），统一用 --profiler-config '{"profiler":"torch","torch_profiler_dir":"./vllm_profile","torch_profiler_with_stack":false}'。

2.2 联动机制：上游骨架四件套，昇腾只换执行器

上游侧（vLLM main）：ProfilerConfig 定义参数； gpu_worker.profile(is_start)（vllm/v1/worker/gpu_worker.py:1297）是入口； WorkerProfiler（vllm/profiler/wrapper.py）是生命周期状态机——管理 delay_iterations（启动后延迟几步再采）、max_iterations（最多采几步）， 每步 worker 循环调一次 step() 推进状态； 工厂 create_worker_profiler（wrapper.py:675）按 profiler 类型发 TorchProfilerWrapper / CudaProfilerWrapper / ProtonProfilerWrapper ——只有 CUDA 三分支，没有 NPU。

昇腾侧（vllm-ascend）：NPU 的 NPUWorker.profile() （vllm_ascend/worker/worker.py:1170）不走上游工厂，直接实例化 TorchNPUProfilerWrapper（worker/worker.py:1177）—— 它继承上游 WorkerProfiler（状态机、延迟/步数限制全部复用）， 只把底下的执行器从 torch.profiler 换成 torch_npu.profiler。 "继承骨架、替换执行器"就是这条线的全部联动设计。

2.3 产物与 PD 分离注意

停采集后 torch_profiler_dir 下出现 *_ascend_pt 目录，先调 torch_npu.profiler.profiler.analyse() 解析，再看 ASCEND_PROFILER_OUTPUT： kernel_details.csv（内核级）、operator_details.csv（算子级）、 op_statistic.csv（算子利用率）、step_trace_time.csv（步调度）、 trace_view.json（Chrome tracing，用 MindStudio Insight 打开）—— 这正是半年目标 KR1.3 里"profile 分解 Cube/Vector/通信"的数据来源。

PD 分离下 P/D 是两个独立实例：两边都要带 --profiler-config（目录错开）， 负载均衡代理不转发 /start_profile、/stop_profile——必须分别 curl 各节点； EPD 代理（layerwise）则支持向全部 E/P/D 实例广播。

3.2 符号表机制：vllm-ascend 把"打点清单"生成好

线二的核心配置是一份符号表 YAML：声明"哪些函数要打点、用什么 handler 记录"。 vllm_ascend/profiling_config.py 在 vLLM 启动时自动生成 ~/.config/vllm_ascend/service_profiling_symbols.<版本>.yaml （文件名带 vLLM 版本号，generate_service_profiling_config L538 原子写入）。 清单覆盖服务全链路，且每条可带 min_version/max_version——上游接口一变， 换一条符号声明即可，这是它对齐上游快速演进的关键手段：

  • OpenAI 入口：OpenAIServingChat.create_chat_completion、AsyncLLM.generate
  • 调度批处理：Scheduler.schedule / add_request（上游类 + 昇腾 AscendScheduler 各一条）
  • KV Cache：KVCacheManager.free / get_computed_blocks
  • 模型执行：Executor.execute_model、NPUModelRunner.execute_model / _update_states / _prepare_inputs、logits、sampler
  • 投机/MTP：propose_draft_token_ids 等专用 handler

④ 版本演进与坑（联动风险清单）

  • 环境变量废弃：VLLM_TORCH_PROFILER_DIR 2026-01-19 起废弃（PR #5928），改用 --profiler-config（在线）/ profiler_config（离线）；老文档/脚本里的旧用法要迁。
  • 端点 404：/start_profile、/stop_profile 只在启动带 --profiler-config 时注册——curl 404 先查启动参数。
  • 互斥：msmonitor_use_daemon 与 torch profiler 不能同开（TorchNPUProfilerWrapper 启动即抛错）。
  • stack 开销：torch_npu 的 with_stack 开销显著，wrapper 用 with_modules 等价替代；指南建议默认关 python stack（torch_profiler_with_stack=false）。
  • 接口换代：执行时长打点 ProfileExecuteDuration.capture_async 只支持到 vLLM 0.14.0rc1，0.15.0rc1 起上游换 record_function_or_nullcontext——符号表用双条目按版本分流（升级 vLLM 后符号表自动跟着版本号切换）。
  • PD 分离：P/D 各自配 --profiler-config（目录错开）、各自 curl；普通 LB 代理不转发 profile 端点。
