一、模型速览：890 B/token 是怎么来的

读图指引：这张图回答"890 B/token 的全局 KV 是怎么算出来的"—— 主链上三刀：CED 砍"谁产 KV"（解码器不自己产，从编码器投影），CSA2 砍"读多少"（三模式共享索引），FP4 砍"每份多大"； 旁路三件（Engram / DSpark / SWA Replay）负责让 decode 维持在低 KV 压力下。

二、CED 拆解 × 昇腾现状：KV 的"出身"变了

读图指引：这张图回答"解码器的 KV 从哪来、为什么 prefill 决定一切"—— 编码器 20 层只在 prefill（含 chunked prefill）干活，末端隐状态一次性投影出全局 KV 写入缓存； decode 只消费。看清楚这条主链，第五节的 P1（融合压缩）和 P7（PD 分离）就都有了着力点。

算子契约速记（仓库 QLI 开发者指南 · A3 现状）

  • INT8 Q/K + FP16 头权重，per-head Q / per-token K scale，quant mode 2；32/64 复制索引头，head_dim 128。
  • 位置 TopK ∈ [1, 2048]；候选块为 64 的倍数 ∈ [64, 2048]，块大小固定 8 个压缩位。
  • A2/A3 仅编译上述布局（其他布局被主机校验拒绝）；A5 保留 16 键全模板矩阵；索引器只返回索引与候选 ID，不返回分数。

P1融合 Compressor 算子扩展到 V4.1

现状：ratio-1 就是 wkv + RMSNorm 两个小算子（第二节代码），ratio-2 靠 Triton 环形池化；而 V4 已有按架构选键的融合 Compressor 模板（四键/架构，coff 覆盖压缩比 128/4）。

建议：把融合模板的 coff 扩展覆盖压缩比 1/2（至少先融合 ratio-1 的投影+归一化）；评估把 ratio-2 的 Triton 环形池化下沉为 AscendC。

收益方向：CED 的"编码器→解码器 KV 投影"是本代模型的独有热点路径；prefill 每个源层减少 kernel 启动与中间张量，40 层规模化后收益放大。

参考：仓库开发者指南 deepseek_v41_qli_candidate.md（"V4.1 currently uses small operators for compression"）· 链接

P2FP4 main KV 支持

现状：模型卡明确全局 KV 为 FP4 890 B/token，但 SparseFlashMla 只编 BF16——FP4 的容量/带宽红利一分未得；QLI 的 A5 模板已注册 MXFP4 dtype，说明 FP4 数据通路在 A5 上存在。

建议：给 npu_sparse_flash_mla 增加压缩侧 FP4 cmp_kv 模板 + cache dtype 配置链（kv_cache_dtype → 四槽页容量重算 → prefix cache 兼容性验证）；A2/A3/A5 对 FP4 的硬件支持面先摸底。

收益方向：压缩 KV 体积 ≈×4 下降 → 同卡容纳更长上下文/更多并发；decode 全局注意力读 KV 的 HBM 带宽大幅下降。1M 上下文场景最大单项。

参考：仓库开发者指南编译矩阵节 · 链接

P7CED × PD 分离映射（架构红利）

现状：编码器 20 层只在 prefill 参与，解码器 KV 由末端一次投影——编码器算力天然可锁在 P 节点；仓库 PD 分离与 KV 传输能力已就绪（#16755 / #16910 / #17183 / #16498）。

建议：验证 V4.1 在 PD 分离下的组件归属——编码器+压缩源层驻 P，解码器+Engram+DSpark 驻 D；用 layerwise KV pool 传压缩后 KV（890 B/token，传输量比全量 MLA 小一个量级）。

收益方向：D 节点显存与 KV 压力大降 → decode 批容量上升；P/D 间迁移带宽成本极低。CED 给昇腾部署的独特红利。

参考：#16755 · #16910 · #17183 · #16498

P6decode 双流重叠深化

现状：multistream_preprocess（dsa_v41.py:310，docstring 即"Overlap Q Vector work with KV Cube work"）已覆盖 Q 投影与 KV 写入；同期 #16977 在 DCP 路径验证了 decode 流优化手法。

建议：把 QLI 索引选择（向量型）与 SWA scatter 写入编入同一事件链；对照 #16977 把 V-up 类投影下沉到 Cube 流。

收益方向：decode 每层 Vector/Cube 交替空隙收窄；对 1M 上下文 decode（CSA 读大 KV 占比高）尤其有效。

参考：#16977

P4Engram 主机卸载异步化

现状：prepare_engram（model.py:1049）在层循环前集中查表；主机卸载路径 HostUvaBuffer + gather_dequantize_host_uva（engram/npu.py:173/:275）是同步调用；#17134 已做跨 DP 头分片共享。

建议：查表-反量化挪入辅助流（仓库已有双流框架 multistream_preprocess 可参照）；对 lookback 窗口做逐步预取。

收益方向：decode 步内隐藏 host 内存访问延迟——Engram 196B 参数无法全驻 HBM，访存必经互连。

参考：#17134

P5DSpark 投机解码 × CSA 元数据复用

现状：草稿侧独立维护 SWA KV（dspark.py:212/:275）；同期主线已在 DSA 路径验证两类元数据优化（#17153 组不变元数据缓存、#15949 SAS 元数据优先），均未覆盖 V4.1 的 MetadataBuilder（dsa_v41.py:571/:718）。

建议：两个已验证手法移植到 V4.1 builder；评估 draft 与 target 共享候选索引/topk 缓冲（SharedAttentionState 已保证定址稳定）。

收益方向：每步元数据构建 CPU 开销下降；投机解码净收益（接受长度 × 步成本）上升。

参考：#17153 · #15949

P3A5 上补 CSA 单头特化模板

现状：开发者指南编译矩阵——"single-head CSA specialization is A2/A3-only and split-G/vectorized addressing is A5-only"（A2/A3 编 6 键、A5 编 12 键）。

建议：A5 模板矩阵验证/补齐单头 CSA 特化；若 split-G 实测无损，显式记录结论避免隐性缺口。

收益方向：950DT/A5 服务器上 CSA 层（解码器多数层）注意力延迟；与 P2 同属低风险模板类改动。

参考：仓库开发者指南编译矩阵节 · 链接

六、小结

对照图4 的地图念一遍：P1 / P2 兑现模型设计红利（压缩融合 + FP4 KV，收益最大）；P3 / P6 补齐模板与流水（低风险增量）； P4 / P5 需要 profile 数据确认瓶颈占比后再动手；P7 是部署形态级专项，值得单独立项验证。 两页读完的完整链条：需求怎么来的（前篇）→ 代码怎么落的（前篇）→ 红利兑现了多少、下一步做什么（本篇）。
