参数说明 · vLLM Ascend 可调参数详解

基线：origin/main 26f1363f7（9-13 nightly 同代）· 层4 参数全部带 ascend_config.py 行号与两路源码跳转 · 2026-09-14

五层参数体系：① vLLM 原生启动参数（上游标准，本页层1）② speculative-config（投机解码，15 种 proposer，层2） ③ compilation-config（图/编译模式，层3）④ additional-config = AscendConfig（昇腾私有 pydantic，15 个配置类 91 字段，层4） ⑤ 环境变量（层5，正逐步收编进层4）。日常调优 90% 落在层 4。

层 1 · vLLM 原生启动参数

--tensor-parallel-size

是什么：张量并行：把模型的注意力头与中间维切分到 N 张卡，每步做 allreduce。

深入：TP 组内的通信量与 head 数成正比；GLM-5.2 A5 双脚本均用 TP8（单机 8 卡跑满）。

调优：多机场景优先 DP/EP，TP 一般不超过单机卡数；TP>1 会激活 o_proj TP 切换等分支（GLM 案已证 TP1 下这些分支不触发）。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--data-parallel-size / -local / -address / -rpc-port

是什么：数据并行：每个 DP rank 持有完整模型副本、独立调度器，请求按负载分发。

深入：GLM-5.1-198k 双机部署为 DP8（local 4）×TP4 的 internal-DP 形态；DP 之间通过 rpc-port 组网。DP 下存在 dummy run/idle 同步问题（3e30d711 等）。

调优：增大 DP 提升吞吐但放大尾延迟不均衡；注意 DP rank 间负载不均会放大 prefix 差异。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--enable-expert-parallel

是什么：MoE 专家并行：专家按 EP 维分布在卡间，token 经 all-to-all 路由到所在专家。

深入：W8A8 大 MoE 部署标配（GLM/DSV/Kimi 案 yaml 均开）。EP 与 MC2/AllToAll 通信路径强相关。

调优：EP 下若见精度问题，先排查通信路径（mc2_comm_alg/flashcomm）而非量化本身。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--max-model-len

是什么：KV cache 能容纳的最大上下文长度。

深入：直接决定 KV block 总数与显存占用（133120/202752 这类值即按 128 对齐）。设小了长请求直接拒绝。

调优：不要为省显存设到刚好等于最长请求——预留给 MTP draft 与 hash 对齐余量（hybrid 命中取 LCM 对齐）。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--max-num-seqs

是什么：同时在跑的请求上限（decode batch 的请求维度）。

深入：16/20/32 这类取值直接影响 decode 每步 token 数：32 请求 × MTP4 ≈ 128 token/步（prefix 案中走 batch_matmul_transpose 分支的临界条件）。"Part A"已标注其与算子分支的关联。

调优：调大提升吞吐但推高每步 token 数，可能跨过 BMM_TRANS_MAX_SUPPORTED_TOKENS=1024 这类算子分支阈值。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--max-num-batched-tokens

是什么：单个调度步最多处理的 token 预算（chunked prefill 粒度）。

深入：16384 是 GLM 部署常用值。spec decode 下会被压到 4096 级别（max_num_scheduled_tokens 由 spec 设置，日志有提示）。

调优：与 spec decode 组合时留意日志里的 max_num_scheduled_tokens 提示行。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--gpu-memory-utilization

是什么：模型权重+KV 之外允许使用的显存占比。

深入：0.90/0.92/0.95 常见。PD 分离两端可以不同。

调优：留余量给 activations；调大直接增加 KV blocks（对长上下文命中率无影响）。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--enable-prefix-caching

是什么：前缀缓存：相同前缀的请求复用已算好的 KV blocks。

深入：开关打开≠命中：混合注意力模型走 HybridKVCacheCoordinator，命中是跨 KV 组取最小值。GLM-5.2 案：开关打印正常但实际命中 0%（详见 prefix RCA 报告）。

调优：验证口径用每请求 cached_tokens，不要只看启动日志。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--enforce-eager

是什么：禁用目标模型的 ACL 图捕获，全部 eager 执行。

深入：只影响目标模型；draft 是否走图由 speculative-config 的 enforce_eager 决定（参数 1/2 都给 draft 设了 enforce_eager=true）。参数 2 顶层也加了 enforce-eager → 全 eager。

调优：排障第一开关：任何疑似图/编译问题先加它复测。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--async-scheduling

是什么：异步调度：调度与执行重叠。

深入：与投机解码组合时 cascade attention 会被自动禁用（198k 日志可见 Disabling cascade attention 警告）。

调优：按需开启；排障时先关。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--enable-chunked-prefill

是什么：长 prompt 分块 prefill，避免单次巨长计算。

深入：与 max-num-batched-tokens 配合。

调优：长上下文部署建议开。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--quantization ascend

是什么：启用 vllm-ascend 量化方案（w8a8_dynamic/w4a8/w4a16/mxfp4 等按 checkpoint 自动选择）。

深入：quant method 决定走哪套 quantization/methods 子目录；MoE 重构后文件已按子目录组织（73acadef6）。

调优：checkpoint 与 quant 参数必须匹配。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--tool-call-parser glm47 / --reasoning-parser glm45

是什么：GLM 系输出的工具调用与思考段解析。

深入：aisbench 的 extract_non_reasoning_content 依赖 parser 产出的结构；若精度/格式异常，先核对该参数与 checkpoint 模板匹配。

调优：GLM 部署必配。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

--seed

是什么：采样随机种子。

深入：精度评估固定 1024 保证两次运行可比（GLM 案两版脚本一致）。

调优：对比实验必须同 seed。

源码（vLLM 上游）：vllm/config.py（SchedulerConfig / CacheConfig）· vllm-ascend 侧适配见 platform.py

层 2 · speculative-config（投机解码）

method —— proposer 选择（15 种）

是什么：选择投机解码的起草器。vllm-ascend/spec_decode/ 下有 15 个 proposer 实现： mtp.py（deepseek_mtp，DeepSeek/GlmMoeDsa 专用）、step3p5.py（mtp，Step3.5 式通用 MTP，每个 MTP 层独立 KV 组）、 eagle_proposer.py（eagle3）、dflash/dflash2_proposer.py、dspark_proposer.py、medusa_proposer.py、ngram_proposer.py（NPU 版）、suffix_proposer.py、 draft_proposer.py、extract_hidden_states_proposer.py。

深入：method 决定 KV cache 组结构——deepseek_mtp 是单 draft KV 组（在协调器支持形态内）； mtp 是每 MTP 层独立组（可能超出 AscendHybridKVCacheCoordinator 声明支持的“两类型组合”）。 这是 GLM-5.2 A5 prefix 案的头号嫌疑（详见 pr_learn/prefix_cache_rca_report.html）。

调优：方法一旦变更，务必重测精度 + prefix 命中 + 接受率三项。

源码：vllm_ascend/spec_decode/（15 个 proposer）· GitHub

num_speculative_tokens —— draft token 数

是什么：每步起草的 token 数。GLM-5.1-198k 用 3、DSV32-MTP2 用 2、A5 GLM-5.2 两份脚本都用 5。

深入：越大潜在加速越多，但 draft 变差时浪费越多；同时 max_num_scheduled_tokens 会被压（日志有提示行）。

调优：3 是常用值；AIME 精度评估下接受率可在日志/spec_decode_metrics 中观察。

源码：mtp.py · GitHub

enforce_eager（speculative-config 内）—— draft 强制 eager

是什么：draft 模型禁用 ACL 图。注意它只管 draft：目标模型是否走图由顶层 enforce-eager / compilation-config 决定。

深入：target eager + draft eager 是最保守组合（GLM-5.1-198k 即此形态）；target FULL_DECODE_ONLY + draft eager 也常见。 若 draft 走图且行为异常，先改这里做二分。

调优：保持 true；draft 图化的收益通常被捕获开销抵消。

源码：llm_base_proposer.py（_create_draft_vllm_config 的 runner_type 处理见 748acedf）

层 3 · compilation-config

cudagraph_mode —— ACL 图模式选择

是什么：目标模型的图捕获策略。FULL_DECODE_ONLY（decode 整图 + prefill eager，最常用）、 FULL_AND_PIECEWISE（全图/分段混合）、false（无图）。

深入：图 replay 时注意力块表经 update_graph_params 刷新——窗口内该路径有大变更（827a11d3 PA workspace 复用、 4c9cdea56 input_batch 修复、b0a0aa59c breakable capture）。GLM-5.2 prefix 案的候选 C：图 replay 下新命中的前缀块 若未进入块表 → 等效于没命中。draft 侧另有 aclgraph 捕获（日志 Replaying aclgraph）。

调优：排障第一步通常是加顶层 --enforce-eager 二分；确认性能后可尝试 FULL_DECODE_ONLY 提吞吐。

源码：attention_v1.py（update_graph_params）· compilation/acl_graph.py

稀疏注意力 / DSA 路径（本案核心开关）

enable_sparse_sfa_c8

类型/默认：False · 属于 additional-config.AscendConfig

是什么：SFA 主注意力的 KV cache 打包量化：把 k_nope+k_pe 合并为单个 int8（A3）或 float8_e4m3fn（FP8 平台）张量 packed_kv，配合 scale（fp16/fp32）供 NPU 算子 npu_kv_quant_sparse_flash_attention 做稀疏反量化注意力计算。KV cache 槽位从 [k_nope, k_pe, indexer_k, scale] 变为 [packed_kv, indexer_k, scale, unused]。

深入：生效前提：model_uses_sfa_sparse()（hf config 含 index_topk 且无 compress_ratios，即 GLM-5.1/5.2、DeepSeek-V3.2+ 等 DSA 模型）；同时伴随 q/k Hadamard 变换（L625-629 类级共享静态张量）。【GLM 案实证】0.26.0 得 100 分、0.27.1 起 0 分×3——精度回归的头号定位开关。

调优：精度异常时第一个对照的开关；与 sparse_kv_offload_config 互斥（ascend_config L845-849 校验会 raise）。

源码：ascend_config.py L446 · 本地源码 · GitHub#L446

enable_sparse_li_c8

类型/默认：False · 属于 additional-config.AscendConfig

是什么：Lightning Indexer 的索引缓存量化（与 sfa_c8 是两个独立开关，sfa_v1.py L507 注释明示）。

深入：只对拥有 indexer cache 的层生效；128k_90_50 的 93.33 基线即在 li_c8=true + sfa_c8=false 环境测得。

调优：GLM 案 09-04 dual-nodes 同配置得 93.33 分 → li_c8 单独开不影响精度，说明劣化在 SFA 主路径而非 indexer。

源码：ascend_config.py L447 · 本地源码 · GitHub#L447

enable_dsa_cp

类型/默认：False · 属于 additional-config.AscendConfig

是什么：DSA 跨机上下文并行（DeepSeek V3.2+ / GLM 系 DSA 模型的序列维跨机分片）。

深入：联动：ascend_config L602 自动启用 FlashComm；L650-654 要求 has_indexer + use_sequence_parallel_moe，否则静默关闭；L638-641 警告 PCP 就绪后将废弃 enable_dsa_cp（迁移提示按 TP/PCP 分三档）。GLM 案已实证：dcp_size=1 时 DCP 融合路径（5c59cfba9）不激活。

调优：多机稀疏长上下文部署标配；排查时确认 use_sequence_parallel_moe 是否为 true。

源码：ascend_config.py L394 · 本地源码 · GitHub#L394

编译体系 · 三条编译链与毕昇编译器

链 1 · C++ torch 扩展：csrc/torch_binding.cpp 等（C++17，CMake + gcc/clang）在 pip 构建时编译为 vllm_ascend_C，注册 torch.ops._C_ascend.*（host 侧算子封装，如 batch_matmul_transpose 调用入口）。

链 2 · AscendC 算子：csrc/**/op_kernel/*.cpp（device kernel）经 csrc/build_aclnn.sh 用 毕昇编译器 bisheng（随 CANN 包发布，build.sh 里 which bisheng 检查， 报错原文"bisheng compilation tool not found, Please check whether the cann package"）编译成 ACLNN 算子，依赖 catlass（子模块）。 只有源码构建算子时才需要；pip 官方 wheel 已预编译。头号嫌疑算子 batch_matmul_transpose 的实现即在此链 （csrc/batch_matmul_transpose/op_kernel + op_host/tiling），08-19 的 11921514a 曾整体移除该算子。

链 3 · Triton kernel：triton-ascend==3.2.2（requirements 固定）运行时 JIT 编译 vllm_ascend/ops/triton/*.py（dsa_cp、lightning_indexer、slot_mapping、eplb、compute_slot_mapping 等）。

链编译器触发产物与本案关系
1gcc/clang（CMake）pip 构建vllm_ascend_C—
2bisheng（CANN 内）csrc/build_aclnn.shACLNN 算子二进制★头号嫌疑算子的宿主链
3triton-ascend JIT运行时Triton kernel算子融合开关（fuse_norm_quant 等）作用层

版本错配提醒：Python 侧分支（sfa_v1.py 调用）与 C++ 产物（.so）由不同时间点构建时，可能出现“Python 以为算子在、C++ 已删”的静默回退（GLM 案 prefix 0% 的背景之一）。自编译部署务必保证 Python 与 csrc 同一 commit。

使用建议：调优顺序 = 层4（业务开关）→ 层2（投机策略）→ 层1（并行/批参数）→ 层5（通信/内存微调）→ 层3（图模式）。 任何一次只改一个变量；精度对照必须同 seed、同数据集、同判分规则。
